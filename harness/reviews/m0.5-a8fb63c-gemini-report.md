## 五、架构边界与本轮专项审查核对结论（实测 + 代码推导）

1. **`oot-core` 纯净性与单向依赖（实测通过）**：
   - 检查 `packages/oot-core/src/*.ts` 全部文件，无任何 `node:*`、`fs`、`process`、`Date`、`Math.random`、`window` 引用；所有状态变更均通过 `dispatchCommand` 纯函数入口完成。
2. **非法命令回滚与幂等性（实测通过）**：
   - `dispatchCommand` 在 `try` 块内对 `original` 执行深拷贝后操作，任何 `requireRule` 失败均进入 `catch` 并原样返回 `original` 引用、`events: []` 及错误码，不会污染状态、账本或 RNG 流。

3. **ViewModel 引用隔离（实测通过）**：
   - [simulation.ts](file:///D:/Documents/FeiyangChen/devApps/ai-game/out-of-tokens-review-gemini-a8fb63c/packages/oot-core/src/simulation.ts#L385-L388) 对 `actors`、`skills`、`modes`、`jobs`、`weights`、`qualityLines`、`team`、`pending.choices.effects`、`ledger`、`resources` 均做了浅/深拷贝隔离，修改 ViewModel 返回对象不会污染 `State` 或 `Content`。
4. **存档损坏、版本不兼容与超长命令序列拒绝（实测通过）**：
   - [index.ts](file:///D:/Documents/FeiyangChen/devApps/ai-game/out-of-tokens-review-gemini-a8fb63c/packages/oot-persistence/src/index.ts#L27-L43) 严格校验 `schemaVersion === 1`、`engineVersion`、`contentVersion`、`contentHash`、`commands.length <= 100000`、回放命令无报错及最终 `stateHash` 一致性。
5. **多阶段（`multi`）与长期合作（`retainer`）财务结算（代码推导 + 实测）**：
   - `multi` 与 `retainer` 在首阶段交付（`j.phase === 0`）时扣除首付预付款 `j.advance`，随后将 `j.advance` 置为 `0`（`simulation.ts:343, 358`），后续阶段正常按里程碑结算，若后续阶段违约不会重复退还首阶段已抵扣的预付款。唯一缺陷在于 `retainer` 恢复槽的状态切换时机（见 `GEM-a8fb63c-02`）。

## 六、未覆盖范围与剩余风险

1. **大样本保留区间 `3001–4000` 未占用**：按审查指令要求，本轮仅使用了 `4001–4020` 共 20 个随机种子（100 局），将 `3001–4000` 完整保留给主线程后续回归验证。
2. **`greedy` 与 `value` 策略的净现金差距（设计建议 / 剩余风险）**：
   - 在 `1..1000` 基线样本与 `4001–4020` 独立样本中，`greedy` 策略的中位净现金均略高于 `value` 策略（`4001–4020` 中 `greedy` 为 `¥22,906.03`，`value` 为 `¥20,975.15`）。原因是 M0.4 降低了委托工作量上限（`<= 40`）并提高了配额，使得无脑抢高额单的违约惩罚率较低。这不违反当前 `gates()` 的四项硬门槛，但在 M1/M2 引入更复杂委托组合时，建议关注高复杂度浑浊委托对 `greedy` 策略的区分度。
3. **M1 Web UI 与状态机对接风险**：
   - 若不先修复 `GEM-a8fb63c-01`（危机状态判断用 `s.cash` 而非 `s.crisisSince`）和 `GEM-a8fb63c-02`（`retainer` 在 `slot === resumeAt` 仍为 `waiting`），M1 前端在渲染“危机横幅/接单按钮禁用态”与“长期合作委托恢复当日的排班操作”时会出现 UI 状态与底层规则不一致的 Bug。因此强烈建议在启动 M1 UI 开发前先合入这两处最小修复并补充对应回归测试。
