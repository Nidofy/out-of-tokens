## 0. 三个总判断

### 0.1 可玩性风险：**高**

现在的 M0.2 已经形成了一个能跑通的循环，但还**不是一个有策略的经营游戏**。实测里，几乎所有"决策"都会收敛到同一个固定答案：

1. 4 人一起上同一个委托（3 名执行 + 1 名审查），一次只做一单；
2. 委托一定要澄清；
3. Qwen 必须上场；
4. 不用负责人（Planner）；
5. 事件卡固定选第一个选项。

成本与能力的取舍不存在：Token 从来不会不够用，单价这个属性对结果没有影响。时间与质量的取舍也不存在：良好档（75）在实测中**一次都没出现**。

### 0.2 经济健康度：**不健康，但离目标的差距可以量化，靠调配置就能修**

- 14 天固定支出是 2×¥2,300 + ¥8,000 = **¥12,600**。启动资金 ¥5,000，所以至少要赚 **¥7,600** 才能在第 14 天保持现金不为负；要达到 GDD §4.3 的"结余 ¥1,000–3,000"，需要赚 **¥8,600–10,600**，也就是每天 ¥614–757。
- 我能找到的最好策略是 **每天约 ¥481**（14 天赚 ¥6,734，第 14 天平均现金 −¥1,122，90 分位 −¥30）[实测 200 种子]。所有策略在第 14 天现金不为负的比例都只有 **0–10%**。第 28 天时，仓库自带的 value / greedy bot 破产率分别是 **82% / 75%** [实测 100 种子]。
- **从数学上说任务不是不可能完成**：4 人全员执行的理论产能上限大约 826 WP / 14 天，按 bugs 单价折算约 ¥14,000 [推演]。但现实策略比"刚好不亏"还差 13%，比 GDD 目标差 28–57%。
- 没有找到无限刷钱或白拿资源的漏洞。发现一个只在理论上成立的"刷预付款重置危机计时"路径，记为 P3。

### 0.3 M0 是否可以继续推进：**可以有条件推进**

- 工程上，M0.3 的内容扩展（30 个模板 / 20 张卡）可以继续做，不需要等平衡修好。
- 但在 OPUS-01 到 OPUS-05 解决之前，**M0 不能宣布"派遣决策有取舍"**（GDD §20.1 的 M0 验收目标），也不该开始 M1 的试玩问卷。
- 最需要先修的是两个**配置层面**的问题：质量线上限（OPUS-02）和 Token 配额（OPUS-05）。很多其它问题都是这两个问题的连锁反应。

## 2. 经营对照案例（全部为实测，同一组种子 1–300，委托在第 0 时段注入，事件固定选第一个选项）

列含义：**交付率 / 违约率 / 返工率 / 平均质量 / ≥75 的比例 / 平均到手（含预付和违约罚金） / 每"人·时段"扣除 Token 后的净收益**。Token 统一按临时购买价 ¥0.5/T 估算（这是上限），本地算力按 ¥0.1/单位估算。

### 案例 A：`bugs`「修一下网站，就一个小地方」

条件：40 WP、期限 4 个工作时段、¥700、清晰度 60（2 条隐藏需求）。

| 派遣 | 澄清 | 交付 | 违约 | 返工 | Q | ≥75 | 到手 ¥ | 每人·时段 ¥ |
|---|---|---|---|---|---|---|---|---|
| DeepSeek+Qwen 执行 | 否 | 0.95 | 0.05 | 1.00 | 67.0 | 0 | 582 | 48.9 |
| DeepSeek+Qwen 执行 | **是** | **1.00** | 0 | 0.19 | 66.6 | 0 | **680** | **78.3** |
| DeepSeek+Qwen，本地部署 | 是 | 1.00 | 0 | 0.18 | 66.7 | 0 | 691 | **97.2** |
| Qwen 单人 | 是 | 0.80 | 0.20 | 0 | 63.9 | 0 | 348 | 41.5 |
| **GDD §7.3 范例**：DeepSeek 执行 + Qwen 审查 | 是 | **0.00** | 1.00 | 0 | 2.8 | 0 | −210 | −30.4 |
| Mistral+Llama 执行 | 是 | 0.00 | 1.00 | 1.00 | 48.5 | 0 | −210 | −36.8 |
| 3 执行 + DeepSeek 审查 | 是 | 0.75 | 0.25 | 0.52 | 61.6 | 0 | 463 | 29.3 |

**玩家会怎么选**：先澄清，再派 DeepSeek+Qwen，并且用本地部署。

**暴露的问题**：
- GDD 设计文档里的示范组合**100% 违约**。原因是 GDD 假设澄清后工作量会降到 40 WP、期限 6 个时段，但 D013 没有实现工作量下调，DeepSeek 单人产能撑不住。
- 两个低价角色（Mistral、Llama）组队，在这一单上完全没有办法交付。
- 不澄清时，返工率是 100%，但交付率仍有 95%。说明隐藏需求的代价只是"多 20% 工作量的返工"，返工充当了兜底澄清。

### 案例 B：`menu`「帮楼下奶茶店写个菜单」

条件：30 WP、期限 4 个工作时段、¥500、清晰度 90（没有隐藏需求）。

| 派遣 | 交付 | Q | 到手 ¥ | 每人·时段 ¥ |
|---|---|---|---|---|
| **Qwen 单人** | 0.99 | 66.2 | 468 | **85.7**（全表最高） |
| Qwen 执行 + DeepSeek 负责人 | 0.99 | 66.2 | 469 | 39.8（Token 多 26%，期限只快了 0.04 个时段） |
| Mistral 单人（最快、最便宜） | **0.00** | 53.2 | −150 | −46.2 |
| 4 人全部执行 | 0.40 | 58.0 | 112 | 3.5 |
| 3 执行 + DeepSeek 审查 | 0.99 | 64.7 | 489 | 45.0 |
| Mistral+Llama 执行 + Qwen 审查 | 0.91 | 63.0 | 441 | 44.0 |

**玩家会怎么选**：Qwen 一个人做菜单，把其他人派去别的单。

**暴露的问题**：
- **速度越快，质量越被拉低**。质量是按 WP 加权的平均匹配度，Mistral 速度 1.5、匹配度只有 0.54，它产出越多，团队平均质量越低。所以 4 人全执行反而只有 40% 能过及格线。
- 审查者的 +5～7 质量是"能不能过 60 分"的关键，而不是"能不能拿良好"。
- 负责人在这里是纯亏。

### 案例 C：`website`「做个类似微信的简单网站」

条件：60 WP、期限 6 个工作时段、¥800、清晰度 20（3 条隐藏需求）。

| 派遣 | 澄清 | 交付 | 返工 | Q | 到手 ¥ |
|---|---|---|---|---|---|
| Qwen 单人 | 否 → 是 | 0.00 → **0.71** | 0 → 0 | 38.7 → 62.7 | −240 → 303 |
| DeepSeek+Qwen | 否 → 是 | 0.93 → 0.96 | 1.00 → 0.31 | 66.7 → 66.2 | 704 → 755 |
| 3 执行 + DeepSeek 审查 | 否 → 是 | 0.55 → 0.80 | 1.00 → 0.43 | 60.0 → 61.9 | 328 → 588 |

**玩家会怎么选**：一定会澄清。人少、产能紧的时候，澄清的收益最大（单人交付率从 0% 升到 71%）。这个方向是对的。

**暴露的问题**：
- 委托描述直接写了答案："其实社团只需要展示页，先问清楚"。玩家不需要读线索。
- 描述承诺"只需要展示页"，暗示工作量会下调，但代码里**并没有下调**，文案和规则对不上。
- 澄清找谁做效果都一样（固定揭示一条），所以最适合澄清的是闲着的低价角色。这是低价角色在当前版本里唯一的用处，而且不是设计出来的。

### 案例 D：完整 14 天经营（200 种子；28 天的数据用 100 种子）

| 策略 | 第 14 天现金均值 | 90 分位 | 14 天收入 | 交付/违约 | 第 28 天破产率 |
|---|---|---|---|---|---|
| 什么都不接 | −7,600 | −7,600 | 0 | — | 100% |
| 仓库 value bot | −1,873 | −990 | 5,801 | 10.0 / 0.21 | 82% |
| 仓库 greedy bot | −1,686 | −950 | 5,926 | 10.3 / 0.04 | 75% |
| 两组并行（DeepSeek+Qwen 做开发单；Mistral、Llama 负责澄清） | −3,400 | −2,760 | 4,225 | 5.6 / 0.06 | 100% |
| 同上，但**不用 Qwen** | −7,468 | −6,050 | 1,964 | 1.2 / **4.0** | 100% |
| **最好的策略 A**：全员一单 + 澄清 + 按单价（报酬/WP）挑单 + 云端 | **−1,122** | −30 | 6,734 | 10.1 / 0.05 | — |
| 同上，但全员本地部署 | −2,432 | −1,674 | 5,419 | 8.0 / 0.21 | — |
| 4 人全执行、不设审查 | −5,170 | −1,960 | 4,139 | 4.8 / 3.9 | — |

**结论**：
- "全员一单"打败了"并行多单"。根本原因是只有 DeepSeek 和 Qwen 能把质量拉到 60 以上，而它们只有两个人。
- 全员本地部署反而更差。4 人合计每时段约 128 单位，超过 120 的容量，按 ASCII 顺序 **Qwen 会被整人停工**，偏偏它是匹配度最高的执行者。玩家事先无从察觉。
- 所有策略云端 Token 只用掉了日配额总量的 **26–33%**，**没有任何一局需要购买 Token**。

## 4. 逐项结论

**1. 策略深度**

| 决策 | 现在有没有取舍 |
|---|---|
| 接单 vs 拒单 | 没有。有空闲产能就接，拒单等于什么都不做 |
| 澄清 vs 直接接 | 永远澄清 |
| 单人 vs 团队 | 只有 Qwen 单人做菜单这一个例外，其它情况都是全员一单 |
| 高能力 vs 低成本 | 没有，成本这个维度不存在 |
| 深度思考 vs 快速执行、现在交付 vs 继续审查、加班 vs 保精力 | 都没实现，或者没有可选项 |

存在明显的长期最优固定策略（§0.1）。

**2. 经济系统**：见 §0.2 和 OPUS-01、05、13、14。拒单永远不是最优策略：什么都不接会落到 −7,600，比任何接单策略都差。

**3. 四个角色**：
- Qwen 必选（菜单单的核心）；
- DeepSeek 次要必选（开发单的核心，也是最好的审查者）；
- Llama 和 Mistral 只能当填充执行者或"澄清工具人"；
- Llama 没有任何专长：游戏里没有偏创意的委托，而创意正是它唯一的相对优势；
- 不用最高属性的角色**拿不到更好的收益**。

这个结论只针对四角色阶段，不能外推到完整的 12 角色。

**4. 委托与甲方**：
- 已实现：澄清的成本（占一个人一个时段），以及惩罚可预期（隐藏需求必然导致一次返工，不会无预警重罚）。
- 有问题：文字线索太直白、文案与规则不一致（OPUS-09）。
- 谈判和需求变更**没有实现，无法评估**。

**5. 事件**：只有两张卡，都不改变决策（OPUS-11）。强制等待只影响 DeepSeek 一个人的一个时段，频率可以接受，没有破坏经营。小费卡的梗还没和机制结合起来。

**6. 节奏**：
- 每个游戏日只有 2–3 个有效命令（接单、派遣、交付），对 CLI 原型来说偏少，但没有烦琐的重复操作。
- 失败原因可以解释，但 CLI 没有显示质量的分项构成（匹配、审查、隐藏需求、缺陷、波动），玩家看不懂为什么 4 人全执行反而不及格。建议在视图模型里加上质量分项。
- 角色状态不构成管理负担，因为它们根本不起作用。

## 5. 下一轮平衡实验

所有实验都要在固定 SHA 上跑，≥200 种子，**同一组种子**跨方案对比。

1. **E1 质量线扫描**：`qualityLines` 分别取 60/75/90（现状）、60/72/85、60/70/80，看良好/惊艳档的比例，以及"审查 vs 多一个执行者"哪个更赚。
2. **E2 配额与单价扫描**：日配额 {150/300, 200/400, 300/600} × 单价倍率 {1, 1.5, 2}，看"Token 用光"次数、购买金额、各角色进入最优组合的次数。
3. **E3 收入系数扫描**：报酬 ×{1.0, 1.2, 1.35, 1.5}，以及工作量 ×{1.0, 0.8}，用策略 A 和随机 bot 对照，找到同时满足"A 第 14 天结余 ¥1,000–3,000"和"随机 bot 破产率 40–70%"的区间。
4. **E4 去角色实验**：去掉 Qwen、去掉 DeepSeek、去掉 Mistral、去掉 Llama，各跑一组，看收入下降多少（衡量每个角色的边际价值）。
5. **E5 岗位实验**：3 人团队里比较"负责人 + 2 执行"、"2 执行 + 审查"、"3 执行"，每个模板单独跑。
6. **E6 并行实验**：加入协作成本系数之后，比较全员一单和两组并行。
7. **E7 澄清实验**：只对比"澄清"与"不澄清"两种 bot，看小白甲方委托的违约率之比（GDD §16.8 要求 ≥2 倍）。
8. **E8 本地容量实验**：本地容量 {0, 60, 120} × 是否显示超容预警。

## 6. 需要补充的统计指标

- **逐委托**：用了多少人·时段、Token 折合金额、质量分项、是否返工、返工原因（隐藏需求/缺陷/匹配度不足）。
- **逐角色**：派遣率（按人·时段算，不按派遣次数）、作为执行者/审查者/负责人/澄清者的次数、对交付的边际贡献。
- **经济**：每日现金曲线、第 14 天现金 ≥0 的比例、扣欠费前的现金（P10/P50/P90）、配额使用率、Token 购买金额、"Token 用光"次数、本地超容停工次数。
- **质量**：各档位分布（未达标/及格/良好/惊艳），以及"差一点就进下一档"的比例（距离档位线 ≤3 分）。
- **事件**：每张卡的触发次数、每个选项被选的比例、选每个选项对收益的影响。
- **决策密度**：每个游戏日的有效命令数，以及"可选方案中收益差距 <10% 的决策点"占比（衡量决策有没有张力）。

## 7. 当前 M0 还不能验证的设计

- 完整 12 角色的平衡、开源/闭源双轨、闭源席位费、"旗舰 vs 合理搭配"毛利率指标（D010 已延后到 M2）。
- 谈判、拆分阶段、需求变更、加隐藏标签/约束类隐藏需求、多轮/长期/SLA/急单/竞标等交付模式。
- 深度思考、加班通宵、心情、压力、好感、协同羁绊、特性、成长。
- 硬件、软件研发树、Token 套餐升级、声望等级与声望衰减、交付后爆雷。
- 贷款、债务螺旋、难度模式、继承式重开，以及"危机中 70% 翻盘"这一目标。
- 20 张事件卡里的绝大多数，以及"负面事件可以预防"这一原则的整体落实。
- 小镇生活、找人、多场景对经营的影响。

## 8. 对 Codex 下一阶段的放行意见

**结论：有条件放行 M0.3。**

1. **可以继续**：M0.3 的内容扩展和 B01 bot 改造。但新增内容要配合本报告的配置调整：新模板请带上 `qualityLines`，并覆盖 Llama 和 Mistral 能当主力的委托类型。
2. **集成前必须修（P1）**：
   - OPUS-09 的文案改正（零成本）；
   - OPUS-06 的本地超容提示或拒绝派遣；
   - OPUS-07 / OPUS-08 两条一行公式，需在 DECISIONS 里登记。
3. **M0 平衡验收前必须修（P0）**：OPUS-01 和 OPUS-02，并用 §5 的 E1–E3 证明达到了 GDD §4.3 和 §16.8 的目标。在此之前，STATUS 和 Review Packet 应继续明确写"经济未达标"。现有文档已经这样写了，值得肯定。
4. **流程**：审查快照必须和开发目录隔离（见文首警告）；正式批量统一用 ≥200 种子；每轮都附上本报告 §6 的指标。
