**我的结论是：最新实现已经具备“视觉定型”的基础，但还没有达到可以冻结整体美术与 UI 风格的程度。`UI_ART_DIRECTION_1109.md` 的方向总体合理，作为修复清单和制作约束较扎实；但它还需要升级为“整屏视觉规范”，而不只是材质、颜色、字号和资产制作规范。**

这轮建议明确调整开发重心：

> **暂缓新增玩法，先完成主界面、委托工作台、伙伴档案三张完整样板，统一界面层级、角色呈现、场景空间与交互反馈，再批量推广到其他页面和场景。**

不需要换引擎，也不需要再重画一套角色。当前最值得做的是把已有资源和功能真正整合成一个完整的游戏视觉系统。

## 审查基线与验证范围

本轮读取的默认分支为 `codex/m1-foundation`，HEAD 为 **`7e511b3`**；它主要更新交接记录，对应的实现提交是 **`d376e1c`**，版本为 **engine 0.16.0 / content office-2**。你提到的文档在仓库中的路径是 `docs/UI_ART_DIRECTION_1109.md`。[GitHub](https://github.com/Nidofy/out-of-tokens/commit/7e511b308fc54bf9bd7407df53d13c237daf9050)

# 一、最新版本有哪些实质进步？

先明确：上一轮发现的一些问题已经被修正，不应继续作为未完成任务重复安排。

| 方面 | 本轮看到的进步 | 应继续保留的方向 |
|---|---|---|
| 主界面 | 全屏场景、少量悬浮入口，整体比早期管理面板清爽 | 保留场景优先，不恢复常驻大侧栏 |
| 主要操作 | 主按钮恢复了明确的填充与对比，不再只是裸文字 | 进一步区分主次操作，而不是再次换皮 |
| 角色与工位 | Qwen 标准工位遮脸已经调整；家具不再只是最初的硬边矩形 | 在当前构造上精修，不推翻角色或重新生成全部资产 |
| 世界空间 | 背景、人物、家具使用共同的逻辑世界与相机 | 保持普通弹窗不移动、缩放世界 |
| 角色标签 | 已与世界缩放分离，不能再直接套用上轮“12 人时文字缩成几像素”的结论 | 接下来检查标签层级和信息密度 |
| 派遣和反馈 | 已有派遣错误说明、条件预估、实际评级与经营反馈 | 重点转向信息组织和操作过程 |
| 工程实现 | 角色和家具实例已有保留；工位加成显示增加了规则验证 | 不把已修复的重建或加成问题重复列为现状 |

这些进步可从最新截图、办公室实现和集成记录中确认。特别是截图中的工位已经有柔影、渐变、单屏和坐姿修正，不能继续按早期简笔占位资源来评价。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/harness/ui-art-review-1109/integration-standard-1280.png)

不过，**“比之前清爽”与“已经形成干净、高级的视觉系统”之间，仍有一段距离。**

目前我看到的主要差距不是缺少装饰，而是：

**界面的主次层级不够明确，复杂操作仍像长表单，角色与环境的细节和光影尚未统一，部分视觉设计被 CSS 和交互实现直接破坏。**

# 二、应该怎样理解“类似《原神》《星铁》的干净、高级”？

这里不建议把目标翻译成“多用金色、半透明、圆角、毛玻璃”，也不建议直接复刻它们的素材、字体和装饰。

我建议把你希望获得的感觉，转化为下面这些可执行目标。**这是针对本作的设计建议，不是对两款商业游戏官方规范的引用。**

| 你希望获得的感觉 | 在《Out of Tokens》中应如何落实 |
|---|---|
| 干净 | 默认画面只显示当前决策需要的信息，而不是把所有系统同时露出来 |
| 精致 | 字体、间距、边框、图标、材质、动效有统一规则，而不是每个页面单独美化 |
| 有游戏感 | 角色和场景承担主要情绪表达，UI 负责组织决策，而不是让角色成为表单背景 |
| 有层次 | 主操作、次操作、状态信息、装饰的视觉权重明确不同 |
| 有角色吸引力 | 角色详情有足够的展示面积，动作、表情和状态能够被看见 |
| 操作顺畅 | 看需求、比较角色、确认方案、得到反馈形成连续过程，不靠反复切面板和长距离滚动 |

因此，我建议这轮统一的视觉目标定为：

> **温暖的工作室世界，克制清晰的界面，伙伴承担主要情感表达。**

这句话与当前世界观兼容，也不会把游戏突然改成冷色科幻控制台或“全屏黑金”的另一种产品。

其中有一个关键分工：

- **温暖感主要来自场景**：木材、自然光、植物、人物生活。
- **高级感主要来自 UI 的秩序**：清楚的字级、对齐、分组、主次和状态。
- **亲近感主要来自角色**：熟悉的原版形象、合适的展示尺度、自然动作和回应。

不需要要求场景暖、按钮暖、边框暖、所有面板也都重棕重金。那样反而容易失去轻盈感。

# 三、当前实现中应优先修复的具体问题

## 1. 角色详情的大头像，实际上被压成了列表头像尺寸

**这是本轮已独立复现的问题，不是审美意见。**

相关路径：

```text
apps/web/src/studio-ui.tsx
apps/web/src/style.css
apps/web/src/village-ui.css
apps/web/src/alpha-app.tsx
```

角色详情使用了大头像变体；原样式给它设置了 `140×160`，窄屏下也有单独尺寸。但后加载的通用规则：

```css
.studio-app .portrait
```

把它统一覆盖为 **`44×52`**。这个规则也会覆盖地图、候选列表等本来有独立尺寸的头像。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/apps/web/src/studio-ui.tsx)

我用实际选择器和加载顺序在 Chromium 中复现，桌面 `1280×720` 和手机 `390×844` 的详情头像最终都是 **44×52 px**。

这直接破坏了角色档案的视觉中心：本来应该先看到角色，再看状态，现在变成了“小头像旁边堆很多文字”。

### 建议修法

不要继续添加更强的全局选择器覆盖。

应该把 Portrait 做成职责明确的变体，例如：

| 变体 | 用途 |
|---|---|
| `map` | 地图和位置提示 |
| `list` | 普通伙伴列表 |
| `candidate` | 派遣候选卡 |
| `profile` | 伙伴档案主要展示 |

每种变体独立定义尺寸和裁切方式，避免通用 `.portrait` 再覆盖全部场景。

**这项应在任何新一轮角色界面美化前完成。**

---

## 2. 桌子前景的透明点击区，可能挡住角色点击

**这是源码和几何检查支持的高可信风险，但本轮没有在完整 Pixi 游戏中运行点击链，因此还不能写成已经实测确认的运行时缺陷。**

当前家具前后层都有一块完整矩形 `hitArea`，前景层又位于角色之上。这个矩形覆盖到桌子上方，包括与角色头脸重叠的透明区域。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/apps/web/src/office-scene.ts)

Pixi 的自定义 `hitArea` 会参与命中检测；不能因为那一部分看起来透明，就认为点击会自动穿过它到达下面的角色。[PixiJS](https://pixijs.com/8.x/guides/components/events)

可能产生的用户感受是：

> 我明明点了角色的脸，却打开了工位或布置相关界面。

### 建议修法

**把视觉遮挡和交互命中分开。**

桌子前挡板仍然可以遮住角色腿部，但可点击区域应缩到真实的桌面或物体轮廓，或者由独立交互层管理。

不要简单把角色全部放到家具前面来修点击，那会破坏坐姿遮挡。

至少增加五个回归点：点击脸、身体、桌面、家具透明处，以及通过键盘选择对象。

---

## 3. 当前“分区视角”同时在筛掉人物，而不只是移动镜头

当前办公室相机已经比上轮合理，但 `office-scene.ts` 中还会根据当前区域控制角色是否可绘制。

因此，选择 `work-left` 等视角时，**不属于该区域的角色即使投影进入画面，也可能被隐藏**。窄屏初始视角又主要根据第一次同步时是否已有预约确定，后续派遣不一定自然让玩家看到刚刚开始工作的角色。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/apps/web/src/office-scene.ts)

这需要先明确产品语义：

- “切换视角”应该主要改变镜头。
- “只看工作角色”才是筛选。
- 两者不宜在没有提示的情况下混在一起。

### 建议调整

继续保留局部视角，不要求手机同时显示全部 12 人；但增加明确的：

**定位伙伴、定位任务、返回全景、离屏位置提示。**

普通打开弹窗不能自动移动世界；用户点击“定位”才移动。这样既保持空间稳定，也能让玩家找到正在工作的角色。

**不能为了画面干净，让人物在玩家没有理解原因的情况下消失。**

---

## 4. 文档要求关键数值不能使用 11 px，但实现仍存在

我独立复现了两处：

- 账本金额继承 `.ledger-row` 的 **11 px**。
- 精力代价、部分加成标签使用 `--fs-xs`，也是 **11 px**。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/apps/web/src/style.css)

这与文档自己规定的“11 px 只用于非关键元数据”不一致。

建议把字号按信息重要性固定下来：

| 内容 | 建议起点 |
|---|---|
| 正文、操作说明 | 14–16 px |
| 重要金额、关键状态 | 16–20 px |
| 次级解释、单位 | 12–14 px |
| 时间戳、非关键附注 | 可使用 11 px |

这些是本作的建议范围，应在真实画面中确认，不是商业游戏的官方尺寸。

同时注意：**44 px 点击热区达标，不等于里面的文字和图标已经看得清。** 热区、可见图形、文字字号要分别验收。

---

## 5. 浅色金色适合装饰，但不适合直接兼任焦点色

当前浅色主题的黄铜色同时参与装饰和焦点描边。我对不透明基准色进行了计算：

| 色彩组合 | 对比度 |
|---|---:|
| 黄铜 `#c8a262` / 实底 `#fcf6eb` | **约 2.22:1** |
| 正文 `#332922` / 实底 | 约 13.18:1 |
| 辅助正文 `#6e5c4d` / 实底 | 约 5.91:1 |
| 深色主题黄铜 / 深色实底 | 约 8.40:1 |

所以，**不是整套配色缺乏对比度，而是“装饰色”和“关键交互状态色”职责混用了。** 色值来自当前 tokens，具体透明叠加还需要在真实背景上测量。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/apps/web/src/tokens.css)

对于需要被识别的控件状态，3:1 是有用的非文本对比度基准；这不代表每一条纯装饰边框也必须满足它。[W3C](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

建议拆分：

```text
accent-decor
focus-ring
selected-indicator
```

焦点可以使用更深的强调色或明暗双环。**不要为了让焦点可见，把所有装饰金都加深。**

# 四、视觉层面最需要调整的，不是配色，而是界面结构

## 1. 主界面：现在清爽了，但控件的视觉权重仍然过于接近

最新截图中，常驻入口大多使用深色胶囊、细金边、阴影和透明材质。这比早期散乱面板统一，但也带来了新问题：

**资源、导航、时间、普通操作和主要行动，长得比较相近。**

窄屏则主要通过隐藏资金和额度来减轻拥挤。对于经营游戏，这种处理虽然让画面简洁，却提高了读取核心信息的成本。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/harness/ui-art-review-1109/integration-standard-1280.png)

### 推荐的主界面层级

我建议保留现有四个主要入口，但重新组织视觉权重：

| 层级 | 内容 | 表现 |
|---|---|---|
| 主行动 | 推进时段、当前必须处理的事件 | 最明确的填充与对比 |
| 经营状态 | 资金、额度、时间 | 组合成稳定的状态组 |
| 常用入口 | 委托、伙伴、工作室、手账 | 轻背景或弱边框，不与主行动抢重心 |
| 情境信息 | 即将到期、待验收、伙伴异常 | 按需要出现，不长期铺满 |
| 装饰 | 小面积金属、纹样、光效 | 不承担关键信息 |

手机可以保留紧凑的资金/额度摘要，把低频操作收进“更多”，而不是优先隐藏经营核心数据。

角色姓名和加成也应有层级：平时轻量，选中或异常时展开。不要让每个人长期顶着完整姓名、活动、精力、加成等多行标签。

---

## 2. 委托派遣：应从长表单升级为“任务工作台”

当前功能已经比较完整，但阅读顺序仍主要是：

**需求 → 协商/澄清 → 设施说明 → 全员岗位 → 预估 → 假设说明 → 风险 → 确认。**

当名册扩大时，玩家需要在一个长弹窗中不断滚动。原生下拉框本身不是问题，问题是界面没有充分区分“理解任务、比较候选、确认方案”三个阶段。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/apps/web/src/alpha-app.tsx)

### 建议的桌面工作台

| 区域 | 内容 |
|---|---|
| 需求区 | 客户描述、已知要求、预算、截止时间 |
| 组队区 | 岗位槽、已选成员、可用候选 |
| 结果区 | 工期、资源、质量区间、风险 |
| 固定确认栏 | 方案摘要、取消、确认派遣 |

它可以是较宽的聚焦浮窗，**背后的场景保持原相机不动**，不必变成新的永久侧栏。

候选人应该能直接比较：

> 头像、擅长方向、当前状态、是否被占用、预计成本。

不要要求玩家先去伙伴页记住属性，再回到派遣页操作。

预估条件应保留，但可以折叠为简短说明。当前有条件质量区间，不应为了看起来直观而擅自改成没有统计依据的“成功率”。

窄屏可以分步展示需求、队伍、结果，但确认摘要和错误原因必须始终容易找到。

---

## 3. 伙伴档案：先展示角色，再展示系统

现在的角色详情把介绍、状态、技能、动作、版本、训练和故事放在一个连续区域里；大头像又被 CSS 缩小，进一步加重了“资料表”的感觉。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/apps/web/src/alpha-app.tsx)

我建议分成三个视觉层次：

**第一层：角色。**
使用已有原版头像或纸娃娃的大展示，名称、当前状态、简短性格介绍。

**第二层：当下可做的事。**
例如查看工作、定位、当前可用互动。只突出少量常用操作。

**第三层：长期信息。**
能力与版本、成长、回忆/故事分区，不全部同时展开。

这里完全不需要新增一批大立绘。**先把已有角色展示正确，比重画人物更划算。**

---

## 4. 布置工具：功能已经有基础，但仍显露内部数据结构

布置工具已经有草稿、费用预估和提交能力，这是值得保留的。但界面中仍出现 `work-1` 等内部槽位、原始库存文字和大量操作按钮；槽位点击主要执行移动，选择对象又在库存中完成，用户意图容易混淆。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/apps/web/src/office-editor.tsx)

建议只改交互表现，不扩大玩法：

- 槽位使用玩家可理解的位置名。
- 家具使用缩略图而不只是型号文字。
- 明确区分“选中家具”和“放到这里”。
- 选中后只突出当前家具可用的位置。
- 保留键盘选择和取消方式。
- 未保存离开时有明确反馈。

**不需要现在加入自由网格、旋转、复杂碰撞或新的房间容量规则。**

---

# 五、美术：最新方向可以保留，但必须先做“完整工作角落”

## 1. 原角色继续保留，统一的是呈现方式，不是人物身份

当前角色仍沿用 AI-Village 原始部件、枢轴和层级，分肢动作也已经存在。后续应继续保留这些资产母版。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/apps/web/src/village-characters.ts)

需要统一的是：

**可见身体尺度、眼线、脚底落点、桌椅接触、前后遮挡、场景光照。**

不要把尾巴、帽子、耳朵等完整外包框当作身高标准，否则角色本体会被错误缩放。

也不要为了让所有人“统一”而给全员套更重的灰黄滤镜。角色的发色、瞳色和标志性配饰是重要识别信息。

---

## 2. 当前三类资产仍存在细节密度差异

从最新截图看，背景较细密，角色轮廓和五官更鲜明，家具则是相对简化的 SVG 构造。最新家具生成器已经加入渐变、柔影、较细描边，因此不应再简单称为“占位矩形”。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/harness/ui-art-review-1109/integration-standard-1280.png)

但**渐变数量增加，不等于三类资产已经统一**。

我建议先完成一个正式工作角落，包含：

> 背景局部、原版角色、基础/标准工位、桌椅遮挡、脚底接触、显示器、键盘、工作道具、主光与阴影。

必须在最终显示尺寸下看，而不是只把单个家具放大四倍检查。

### 这个样板要回答四个问题

**人物是不是这个房间里的？**
脚底、座椅、桌面和地面有合理关系。

**人物是不是正在做这件事？**
手部与键盘、书本、餐具位置相符。

**家具是不是这个背景里的？**
透视、边缘软硬、阴影方向和材质颗粒一致。

**玩家首先看到的是不是该看的东西？**
背景装饰不能比正在工作的角色更抢注意力。

## 3. SVG 管线可以继续使用，但应由视觉样板决定质量

我不建议因为“代码生成的 SVG 看起来不够高级”，就全面改成生成图片。

SVG 仍有可维护、可拆层、可精确标注锚点的优势。真正需要修的是比例、造型、阴影和材质表达，而不是媒介本身。

但也不能反过来认为“所有东西都能画成 SVG，所以就应该全部用几何形状解决”。

建议保留一个受控混合方案：

- 结构和交互层保持清楚。
- 高频家具优先精修比例、边缘和接触阴影。
- 必要时增加少量纹理或绘制层。
- 母版、派生资源、锚点和授权来源独立记录。

这样能保证美术变好时，交互和遮挡不会一起失控。

## 4. 文档中的“左上柔光”应作为制作基准，而非所有场景的绝对规则

统一光源方向对资产生产有帮助，但最终进入不同背景时，仍应检查场景主光。

我的建议是：

**资产有统一的中性制作基准，场景有明确的主光与环境光，角色身份色保持稳定。**

不要在家具一层、人物根节点一层、部件再一层不断叠暖色。最新代码已经减少了重复染色，应保留这个修正，而不是为了整体统一再次加重滤镜。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/apps/web/src/office-scene.ts)

---

## 5. 动画重点应转向接触与衔接，而不是继续增加动作名称

当前已有工作、阅读、用餐和移动差异。下一轮更需要的是：

> 走近 → 到位 → 入座 → 使用物品 → 结束 → 离开。

不必增加新的生活机制，也不必一开始就做复杂寻路。

优先校准四位开局角色，再推广全部 12 人。每位角色的头部、手臂、服装和附属部件不同，不能只复用同一组旋转角度。

同时建议明确一套表现事件协议：哪些角色庆祝、哪些对象闪烁、提示持续多久、何时结束。当前已有 presentation 队列，也有持久 message，两种反馈会同时被页面使用，需要统一寿命与优先级，避免普通成功同时出现回执、Toast 和长期文字。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/apps/web/src/use-game.ts)

# 六、`UI_ART_DIRECTION_1109.md` 是否合理？

## 总体评价

**基本方向合理，但更像“纠偏文档＋制作约束”，还不能单独承担最终视觉规范。**

它最有价值的地方，是清楚保留了角色身份、相机、锚点、前后层、玩法容量和真实性边界；同时没有把已有截图和测试夸大成全部验收完成。文档也明确区分了真实工位效果与仅作视觉预留的等级，这一点应继续坚持。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/docs/UI_ART_DIRECTION_1109.md)

不足主要在于：

> **材质和工程规定较具体，整屏构图、复杂任务界面、角色展示层级和视觉焦点还没有达到可以据此冻结风格的程度。**

下面是对其 A–F 路线的具体建议。左列对应文档现有安排，右列是我的调整建议。

| 文档阶段 | 我的判断与调整 |
|---|---|
| **A：先做工作角落样板** | 正确，但不够。工作角落之外，必须同时看到主界面、委托工作台、伙伴档案三张完整画面。角落漂亮不能证明 UI 已经定型。 |
| **B：统一 UI 样式和组件** | 应从“整理 CSS”扩大到屏幕级信息结构。先决定任务和人物如何展示，再写组件规范。 |
| **C：手机镜头、布局和标签** | 应保留，但验收必须包含交互可达、定位、离屏提示，不能只检查无溢出；“视角是否暗中筛掉人物”也应明确。 |
| **D：批量家具、角色与背景** | 顺序合理，但只能在样板冻结后启动。不要在完整画面尚未统一时批量重画。 |
| **E：继续推进摸鱼与后续机制** | **与本轮目标冲突，应后移。** 视觉阶段只完善已有状态的表现，不增加 O4-B/O4-C 等新的经营规则。 |
| **F：资源、性能与兼容验证** | 应拆成两部分：早期建立基线，后期做完整回归。不能等素材全部制作后才发现字号、解码、缓存和性能问题。 |

原文 A–F 的顺序有利于组织开发，但现在用户目标已经明确为“玩法扩展前先稳定视觉”，因此 E 的位置需要正式改写，而不是继续按旧计划执行。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/docs/UI_ART_DIRECTION_1109.md)

## 文档还需要补充的五项规范

### 1. 三张整屏样板及其标注

不只是色卡和组件截图，而是带真实数据的：

**办公室主界面、复杂委托派遣、伙伴档案。**

每张明确主焦点、阅读顺序、尺寸、留白、主行动、次行动、异常状态。

### 2. 正式字体与语言规则

当前标题字体存在系统楷体、宋体、衬线等回退链。作为开发过渡没有问题，但不同系统可能呈现出不同风格。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/apps/web/src/tokens.css)

我不建议让楷体成为全部游戏标题的默认气质；它容易强化手账或古风感，与现代 AI 工作室并不总是协调。

应提前确认标题、正文、数字的字体职责、实际字重、中文与英文的高度和行距，并核验所选字体的使用条件。**不要到所有页面做好后才换字体。**

### 3. 形状语言

圆角统一不等于所有东西都是胶囊。

建议区分：

| 元素 | 形状职责 |
|---|---|
| 标签、短筛选 | 可以使用胶囊 |
| 主要按钮 | 稳定轮廓、明确填充 |
| 页签 | 选中关系清楚，不必像按钮 |
| 内容列表 | 依赖对齐和间距，不必每行重边框 |
| 大面板 | 少量结构边界，不做多层套金框 |

### 4. 完整状态矩阵

至少覆盖：

**默认、悬停、按下、选中、禁用、焦点、忙碌、失败、空状态。**

“禁用”不能只是变灰；应知道为什么不能用。“选中”不能只靠颜色变化。原生控件可以继续保留，但要与整体字级、间距和状态表达一致。

### 5. 视觉与代码的对应关系

文档应指向实际使用的文件和组件，而不是沿用历史路径。本轮实际入口加载的是 `style.css` 与 `village-ui.css`，后者覆盖前者正是头像问题的重要原因。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/apps/web/src/main.tsx)

建议明确哪些规则属于 tokens，哪些属于组件，哪些属于页面布局，避免继续在末尾追加全局覆盖来“临时修好”。

# 七、建议冻结的视觉规范

以下是我建议新增的规范起点，**不是要求照搬固定数值，更不是对《原神》《星铁》内部规格的猜测**。

| 项目 | 建议 |
|---|---|
| 整体气质 | 温暖现代工作室，界面克制、角色鲜明 |
| 世界色彩 | 木色、自然光、植物、角色身份色 |
| 信息面板 | 较中性的暖白或深灰，避免所有内容都重棕重金 |
| 金色用途 | 少量装饰、选中或主行动强调，不给每个嵌套元素描金 |
| 字号 | 正文 14–16；关键数值 16–20；辅助 12–14；11 仅非关键 |
| 间距 | 使用统一的 4/8 px 系列作为起点，页面之间保持同一节奏 |
| 交互热区 | 延续 44 px 级目标，但视觉图标不必画成同样大的重底圆块 |
| 图标 | 保留现有统一线性基础，统一视觉重量与辨识度，不急于全部重画 |
| 主次操作 | 每个当前操作区只有一个最强主行动，次操作明显弱一级 |
| 面板材质 | 长阅读面板优先稳定可读；透明和模糊只用于合适的小范围 |
| 动效 | 微交互短、明确；复杂面板和结算有独立节奏；减少动态模式可用 |
| 场景相机 | 普通弹窗不动世界；定位由用户显式触发 |
| 角色表现 | 母版不改，按身体/眼线/脚点校准，不按尾巴和饰品外框等比统一 |
| 资产验收 | 在实际显示尺寸与完整界面中验收，不只看孤立原图 |

当前图标已经有统一的基础线条体系，可以继续打磨，不必为了“高级”重做整个图标库。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/7e511b3/apps/web/src/icons.tsx)

特别要强调：**高级感不是增加更多 blur、光晕、噪点、阴影和金线，而是减少无意义差异，让每个视觉信号都有明确职责。**

# 八、接下来的开发路线：视觉冻结优先

建议将下一阶段单独命名为 **Visual Freeze 1**，避免它被新增经营机制不断打断。

| 阶段 | 主要交付 | 放行条件 |
|---|---|---|
| **VF0：范围冻结** | 固定玩法版本、角色母版、允许修改范围 | 不改核心算式、容量、经济、RNG 和存档语义 |
| **VF1：样板与阻断修复** | 三张整屏样板；修大头像、点击区、关键字号和焦点 | 同一视觉语言能覆盖场景、任务、角色 |
| **VF2：UI 结构与组件** | 派遣工作台、伙伴档案、Portrait 变体、按钮/列表/确认栏 | 中英、深浅色、禁用/焦点/错误状态一致 |
| **VF3：场景整合** | 正式工作角落、接触点、遮挡、主光、显式定位 | 人物像在房间中做事，而不是贴在背景上 |
| **VF4：批量推广** | 家具、12 角色校准、食堂/图书馆、章节背景检查 | 样板规则可复用，身份与资产母版不受破坏 |
| **VF5：视觉回归** | 完整截图、交互、加载、失败、离线和性能记录 | 有实际运行证据，而不是只有日志通过 |
| **冻结后** | 恢复 O4-B/O4-C、新章节和新内容 | 新功能使用既定视觉系统，不重新发明一套界面 |

这不要求主线程等待所有美术完成。**VF1 的交互修复、VF2 的界面结构、VF3 的工作角落可以在接口确定后并行。** 但样板未确认时，不要同步量产全部家具和所有背景。

## 连续开发的分工

| 工作线 | 负责内容 | 边界 |
|---|---|---|
| Codex + Astra | 组件、页面结构、镜头、交互、集成和回归 | 唯一主集成线程 |
| 独立美术任务 | 已批准样板的家具、派生资源和锚点数据 | 不修改玩法、存档和角色母版 |
| Gemini 视觉复审 | 固定提交的实际画面、遮挡、比例、适配和交互 | 不能只看源码与“无溢出” |
| Opus/Sonnet 专项 | 操作流程、信息理解、增量回归 | 不与主线程同时改相同文件 |

MiniMax 暂时不应成为开发前置条件。当前主要问题是界面结构、空间关系和纸娃娃动作衔接，不是缺少生成视频。

# 九、怎样判断“视觉已经稳定”，可以恢复玩法扩展？

我建议不要用“已经换过主题”“截图挺好看”作为放行标准，而用下面几项。

### 1. 三张核心界面形成同一套语言

主界面、委托工作台、伙伴档案放在一起时，看起来必须属于同一个游戏；同时各自有明确主焦点，不能全部只是同一种卡片容器。

### 2. 角色在真实尺寸下可辨认、可操作

检查 4 人与 12 人、工作与休息、基础与标准工位。人物脸部不被错误遮挡，点击角色不会落到桌子，重要状态不用放大浏览器才能看清。

### 3. 窄屏只是换布局，不是隐藏关键能力

至少覆盖 `390×844`、`560` 宽度、`844×390`、`1280×720`、`1920×1080` 和超宽屏。检查操作可达、资金/额度可读、定位清楚，而不只是横向滚动条是否出现。

### 4. 深浅色与语言变化不会改变角色和信息层级

角色身份色保持稳定；英文变长、中文换行、200% 字体、减少动态、无模糊效果时，主要操作仍然成立。

### 5. 视觉修改不改变经营结果

相同种子和命令序列，视觉修改前后的领域结果应保持一致。动画跳过、窗口大小和切换场景不能改变资源、奖励或事件随机数。

### 6. 验收证据必须对应当前提交

不要继续拿历史 JPG 或只包含场景的测试页，证明当前 HUD、派遣和档案都已完成。每组证据应标明提交、视口、角色数量、状态和语言。

仓库当前记录也明确保留了真实设备、完整名册、多章节、字体放大和 GPU 性能等未验收项。因此本轮应补的是证据和边界，而不是直接宣布全面视觉完成。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/harness/ui-art-review-1109/integration-results.md)

## 最终建议

**当前最优路线不是“再做得华丽一点”，而是“先让每一层各司其职”。**

场景负责氛围，角色负责情感，UI 负责决策；金色、材质、透明和动画只是服务这三件事的手段。

对于 `UI_ART_DIRECTION_1109.md`，我的最终意见是：

> **保留其原角色、场景空间、资产制作和工程边界；补齐整屏样板、信息结构、字体与状态规范；把 E 阶段新增玩法移出本轮，并把 F 阶段验证前移一部分。**

最优先的实际任务是：**修复大头像和交互命中问题，然后完成“办公室主界面＋委托工作台＋伙伴档案”三张可以直接运行的统一样板。** 这比再增加一批家具、背景或新机制，更能接近你希望的干净、精致的游戏界面。
