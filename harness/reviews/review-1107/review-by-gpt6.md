**总体上，代码仍然在按照 GDD 的方向推进，而且工程实现已经远超最初的 M0/M1；但目前更接近“功能覆盖较广的可运行原型”，还不能视为“GDD 所描述的游戏体验已经完成”。**

接下来的重点不应是继续增加章节、角色、场景数量，而应转为：

> **把第 0 章到第 1 章做成真正可判断、可理解、有角色生活感的游戏，再把成熟做法推广到后续章节。**

这次我核查了默认分支 `codex/m1-foundation` 的核心源码、内容 JSON、Web UI、纸娃娃接入代码、美术资源及验收记录。仓库当前记录的最新角色美术检查点是 `2b47242f236683b540faa6b1885d6267cf98c9f7`，引擎为 `0.11.0`、内容为 `m5-1`。**以下属于静态代码与资料审阅；仓库记录的 138 项测试通过不是我在这里重新运行的结果，也不能替代实际试玩。**[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/harness/reviews/gemini-unified-2b47242-prompt.md)

# 一、现在是否仍在按照 GDD 推进？

## 1. 总体方向没有偏离，但“工程阶段”走在了“产品验收”前面

目前的主要实现与 GDD 对应如下。

| GDD 主线 | 仓库当前情况 | 我的判断 |
|---|---|---|
| 接单—澄清—派遣—执行—验收—经营反馈 | 已有核心状态机、CLI、Web 操作入口、资源和现金流系统 | **主循环已经形成**，不需要重做底层 |
| 多角色、多版本、不同成本与能力 | 已有角色版本数据、部署模式、招募、成长、训练和版本切换 | **基础成立**，但角色差异还需要通过实际委托体现 |
| 一次性、多轮、长期委托与事件 | 当前记录为 108 份委托、64 张事件卡 | **数量已经足够**，质量与策略差异是主要缺口 |
| 第 0–4 章、结局、竞标、远征 | 已有工程实现和合成战役贯通测试 | **流程可贯通不等于正常游玩可通关** |
| AI-Village 风格与原角色复用 | 已切换到原版 12 人纸娃娃及头像 | **方向正确，应固定下来**，不要再重设计人物 |
| 场景切换与角色生活 | 有工作室、食堂、图书馆三类逻辑场景；工作室随章节更换背景 | **有场景基础，但自主生活仍较简化** |
| Web → DSH → PC | 已有 Web、DSH 契约适配和 Windows Tauri 开发构建 | 工程扩展已推进，但真实 DSH 共存、安装和完整产品验收仍有缺口 |

前四项的覆盖和验收边界，仓库自己的 M5 文档也作了区分：合成战役调整了测试内容中的资金、能力、合同，用于证明命令链和状态流程能够贯通，并不证明正常数值下的可玩性。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/docs/M5_ACCEPTANCE.md)

角色方面，最新实现已经保留 AI-Village 原角色的部件、枢轴、层级和四种表情；目前接入的是基础身体动作，不是完整移植行走、工作、用餐和寻路系统。[raw.githubusercontent.com](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/docs/VILLAGE_CHIBI_ACCEPTANCE.md)

场景数量也需要准确理解：**七张背景不等于七个可以独立活动的生活区域**，它们是五个章节的工作室背景，加食堂和图书馆；代码中的逻辑场景仍为这三类。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/apps/web/src/studio-ui.tsx)

## 2. 当前更准确的项目定位

我建议将现阶段描述为：

> **GDD 主要系统已有工程覆盖，进入内容深化、交互完善与正式美术整合阶段；经营平衡和完整体验尚未验收。**

不建议写成“已经完成 M5，开始增加下一批功能”。

原因是仓库仍明确保留了经营平衡问题、真人试玩 `0/10`、正常长局与结局可达性、真实 DSH 验收等开放项。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/docs/ROADMAP.md)

这不是说前面的开发白做了。恰恰相反：**现有代码已经足够支撑下一轮产品化，不需要重新立项或改换引擎。**

# 二、我认为现在最需要解决的五个问题

## 1. 委托数量够了，但不少内容仍然是“换标题的同类任务”

我查看了 `content/campaign/commissions-m5.json`。

例如，网站修复和“类似微信的网站”等任务，仍大量使用通用的需求描述；隐藏要求也出现了重复的“交付格式”“目标读者”一类字段。它们可以验证澄清机制，但还没有充分形成 GDD 所说的“甲方即谜题”。[raw.githubusercontent.com](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/content/campaign/commissions-m5.json)

更值得优先检查的是**任务语义与属性权重不一致**：

- `finale-archive-audit` 是研究类的档案追溯任务，却配置为编码 `0.7`、推理 `0.3`，资料能力为零。
- `finale-slime-label` 是设计类标签任务，也使用编码 `0.7`、推理 `0.3`。
- `finale-museum-voices` 是多媒体短片任务，却配置为写作 `1.0`、多媒体为零。[raw.githubusercontent.com](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/content/campaign/commissions-m5.json)

这些配置并不一定在数学上错误——例如档案追溯也可以被设计成自动化程序开发——但**文案必须说明这种特殊要求**。否则玩家会根据任务内容选择研究、设计或视频角色，却发现真正起作用的是编码属性。

**下一步应该先做“内容—属性—事件—验收条件”的一致性审查，而不是把 108 份委托扩到 200 份。**

---

## 2. GDD 中一些重要决策还没有形成实际操作

目前 `Command` 中已经有接单、拒绝、澄清、派遣、交付、返工等操作，但没有看到 GDD 中独立的“报价谈判”“拆分阶段”命令；团队成员结构中也没有玩家可设置的思考深度。隐藏要求的数据结构主要是文字与附加工作量。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/packages/oot-core/src/model.ts)

因此，当前玩家面对一个模糊委托，主要是在：

> 澄清或不澄清 → 选人 → 推进。

而原 GDD 希望玩家可以进一步决定：

> 澄清哪个问题 → 缩减还是扩大范围 → 是否分阶段 → 是否重新报价 → 用什么团队交付。

**这部分比增加新地图更接近本作的核心竞争力。**

不过，不建议一次性实现完整谈判系统。下一轮只需要先支持一个明确的范例：

> “做一个类似微信的网站”  
> → 澄清后发现真正需要的是社团报名页  
> → 玩家可以选择缩减范围，或者报价更高的分阶段方案。

先让一个委托形成完整的决策链，再抽象出可复用机制。

---

## 3. UI 已经有游戏外观，但核心决策信息还偏工程化

现在的场景主画面、顶部资源、底部四入口和右侧抽屉，是可以继续沿用的结构。没有必要再推翻重做一套界面。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/docs/UI_ART_ACCEPTANCE.md)

但核心操作仍有几个明显缺口：

**第一，派遣预估主要是“本槽资源消耗”。**  
`previewAssignment()` 目前返回的重点是云端和本地资源估计，并没有形成 GDD 要求的完整工期、总预算、质量区间和逾期风险预估。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/packages/oot-platform/src/session.ts)

**第二，界面直接暴露了不少内部表达。**  
委托详情显示“截止槽”，事件选项显示效果类型和值，账本显示内部 `reason` 字段。对开发者来说有用，但普通玩家需要自行翻译它们的含义。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/apps/web/src/alpha-app.tsx)

**第三，存在反馈与结算规则不一致的具体例子。**  
前端将质量达到 `90` 才标为“出色”，但引擎实际按各委托的 `qualityLines` 计算评级；当前一些委托的最高评级线是 `80`。因此某些任务质量为 `85` 时，奖励已经按最高档计算，界面却只显示“达到验收线”。这是从源码可以直接推导出的不一致，值得立即补回归测试。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/apps/web/src/alpha-app.tsx)

**这些问题比换按钮颜色或增加边框更影响游戏体验。**

---

## 4. 角色目前更像“坐在不同背景里的员工”，还没有充分形成生活感

`actorScene()` 的默认逻辑比较直接：标准工作时段回工作室；非工作时段，指定的几个人去图书馆，其余去食堂。尚不是 GDD 中按性格、饥饿、社交、求知等需求进行选择的完整生活系统。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/packages/oot-core/src/campaign.ts)

表现层也主要按人数排列角色和桌椅，再根据状态做呼吸、轻摆、表情等反馈。场景中的位置不是由具体工位、餐桌或书架锚点决定的。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/apps/web/src/scene.ts)

这就造成了一个差距：

> 数据层知道角色在吃饭、学习、工作，但玩家看到的动作与空间关系还不够具体。

不需要现在开发复杂寻路。先做“固定地点＋少量路径点＋动作状态”，就能明显增强 AI-Village 的感觉。

---

## 5. 经营平衡问题需要继续解决，但不能陷入反复追一个统计数字

当前仍开放的 `M05-03`，主要涉及加班收益和小费事件的选项取舍。最新记录中，小费拒绝严格更优的比例为 `34/152 = 22.37%`，未达到冻结协议中的 `25%`。**这个数字是特定机制的诊断结果，不是全游戏通关率。**[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/docs/M5_RULES.md)

下一轮应该重点验证：

> 玩家是否能理解为什么角色状态差、如何恢复，以及“现在多赚一点”和“让角色休息”是否都存在合理适用情境。

不应为了跨过 `25%` 就不断扩大惩罚或提高奖励。原指标、分母和测试队列应保留；若设计上决定调整指标，要单独记录理由，而不是静默改口径。

另外，**旧 M0 平衡实验不能直接替代当前 M5 内容的平衡验证**。角色、成长、设施、剧情奖励和长期合同加入后，需要重新验证完整系统。仓库冻结协议也明确指出了这一点。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/docs/M0.7_PROTOCOL.md)

# 三、游戏内容下一步做什么？

## 建议目标：制作“第 0 章精品体验版”，不删除后续系统

这里的“第 0 章精品版”不是退回 M0，也不是砍掉现有 M1–M5，而是选定一个能够贯穿内容、UI、美术和玩法的质量基准。

我建议范围控制为：

| 内容 | 下一轮建议 |
|---|---|
| 主线 | 第 0 章完整可玩，第 1 章开头有清晰衔接 |
| 核心角色 | 先深化四位开局角色，后续角色保留现有实现 |
| 委托 | 从现有库中精选约 12 份精修，不新增大量模板 |
| 事件 | 精修约 8–10 张，保证不同情境有不同合理选项 |
| 角色内容 | 四位初始角色各两段较完整互动，另加少量双人事件 |
| 场景 | 工作室、食堂、图书馆三处真正可用 |
| 经营体验 | 能理解现金流、成本、截止时间、疲劳和返工原因 |

以上是下一阶段建议范围，不是现有完成情况。

## 1. 先把六类委托做出不同的决策

| 委托样例 | 应当教会玩家什么 | 需要产生的真实区别 |
|---|---|---|
| 奶茶店菜单 | 选择合适而不是最强的角色 | 低成本写作角色可以有较好收益 |
| “只修一个小 Bug” | 先判断真实工作范围 | 澄清后发现多个关联问题，影响工期或报价 |
| “类似微信的网站” | 缩减需求、分阶段交付 | 不是单纯增加 WP，而是改变合同方案 |
| 文献资料整理 | 审查和来源核验的价值 | 高速度不一定等于高可靠性 |
| 临时 PPT 急单 | 截止时间与人员状态的取舍 | 找人、换人、加班各有代价 |
| 周报脚本长期维护 | 稳定收入与人力占用 | 接下后会改变后续接单空间 |

每份委托都应该能够回答：

**玩家读懂了什么线索？因此作出了什么不同决策？结果为什么不同？**

如果只能回答“换了一个名字，工作量多一点”，它就还不是一份值得保留的精品委托。

## 2. 给内容增加“编辑验收”，不要只做 Schema 验证

现有 Schema 能检查字段合法性，但不能判断研究任务为什么只有编码权重。

建议为每份精选委托补一张很短的设计卡：

```text
这份委托的核心判断是什么？
玩家能看到哪些线索？
隐藏要求为什么合理？
至少两种可行方案是什么？
哪些角色有优势，为什么？
成功、返工、拒绝分别有什么反馈？
```

数据检查可以自动识别“类别与能力明显不匹配”的候选，但最终仍由内容审阅判断。不要把“研究任务必须有某个固定权重”写成过于僵硬的规则。

## 3. 新手引导应是连续发生的事情，而不是一段玩法说明

当前界面已有玩法提示文字，但读取到的主界面实现主要还是自由打开面板和直接操作。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/apps/web/src/alpha-app.tsx)

建议将开局做成一条可跳过的引导链：

**第一单完成 → 看懂收入 → 第二单发现需求不明确 → 第一次澄清 → 第一次人员/资源冲突 → 第一次主动安排休息 → 第一次周结。**

关键要求是：

- 允许随时跳过，跳过不改变经营规则。
- 提示能跨存档恢复，不反复出现。
- 每次只教一个新概念。
- 失败原因可解释，不以随机必败来强行教学。

**不要为了教“Out of Tokens”，直接无条件清空玩家资源。** 可以安排一个可预见的资源紧张场景，让玩家通过界面判断和处理。

## 4. 角色故事要从“短句＋加数值”变成“人物经历”

目前剧情数据已经按角色分线，但示例仍多为简短叙述，再提供陪伴或记录一类选项。仓库也明确将其标为未经人工编辑的草稿，而不是已验收剧情。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/content/campaign/m5.json)

下一轮建议先深化少数故事，不扩写全部 60 段。

例如 DeepSeek 的“便宜不是我的全部”，可以与实际经营串起来：

> 连续承担低预算任务 → 角色表达自己的想法 → 出现一个适合深入推理的委托 → 玩家决定是否让其尝试 → 根据实际结果产生不同反馈。

这样，版本解锁、性格和经营才能连接起来，而不是在角色面板里花一笔固定资金就完成全部成长。

原版角色的称谓、外观识别点和关系设定，也应整理成一页角色规范，避免文案与 AI-Village 形象不一致。

# 四、UI 下一步怎么改？

## 原则：保留当前外壳，重做关键任务流程

我不建议再进行一次全面换皮。现有的“场景优先＋四入口抽屉”足以承载这一阶段。

下一轮 UI 的核心任务是：

> **让玩家不打开开发文档，也能判断接不接、派谁、会不会亏、来不来得及。**

### 1. 主场景：增加“现在最需要关注的三件事”

建议在场景旁边增加一个轻量“今日事务”区域，而不是再加一整块管理后台。

只显示最重要的事项，例如：

```text
今日事务
网站修复：明天下午截止，预计还需 2 个工作时段
DeepSeek：心情偏低，今晚休息可改善
房租账单：2 天后到期
```

这些信息必须来自实际状态，不由氛围文本模型编造。

同时把欠费期限、可用人员和待验收任务放到容易发现的位置。不要要求玩家分别打开工作室、伙伴、委托三个面板才能理解当前风险。

### 2. 委托界面：从平铺卡片改为按状态组织

建议保持卡片风格，但拆成：

**待接委托 / 执行中 / 待验收 / 历史交付。**

执行中的任务优先显示截止时间、当前团队、缺口和风险；已经接下的长期任务不能因为列表截断而难以找到。当前界面有统一筛选后取最后 25 项的处理，后续应增加长局列表测试，而不是依赖这一截断来控制界面大小。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/apps/web/src/alpha-app.tsx)

内部的“截止槽 18”改为“第 5 天晚上”，并明确“还剩几个可工作时段”。WP 可以保留，但首次出现时解释为工作量，不应让玩家自行猜测。

### 3. 派遣界面：这是最值得投入的 UI

建议把它做成真正的“委托工作台”。

| 区域 | 需要展示的信息 |
|---|---|
| 任务摘要 | 需求、预算、截止时间、已知风险 |
| 岗位区域 | 执行者、负责人、审查者；支持点选，拖拽作为增强 |
| 候选角色 | 适配度、精力、心情、成本、当前占用 |
| 方案预估 | 预计工期、总资源预算、质量区间、逾期风险 |
| 解释区域 | 为什么这个组合快、便宜或可靠 |

预估需要明确假设，例如“按当前状态、无新增需求变更估计”。不能把有随机事件的任务显示成精确承诺。

还要区分：

**游戏资源消耗、现金支出、已付套餐的分摊成本、项目新增支出。**

否则已经购买的套餐额度可能在 UI 中被错误表现为每次任务都会再次扣钱，影响玩家判断。

### 4. 交付界面：做成游戏反馈，而不是一个分数

建议交付时一次说明：

> 为什么得到这个评级 → 收到多少尾款 → 总共付出了什么 → 角色和客户有什么反应 → 下一次怎样做得更好。

最低限度的失败原因不应全部锁在“可解释性报告”软件后面。该软件可以解锁更精细的技术分析，但玩家在没有购买它时，也应知道自己是因为逾期、未澄清需求，还是缺陷而失分。

评级、奖励倍率、预付款扣除必须统一从核心规则读取，优先修复前述 `90` 分硬编码问题。

### 5. 时间推进：补短演出，不要强制看一分钟进度条

当前主操作是直接发送 `advance`，状态更新后刷新界面，没有实现 GDD 中完整的时段播放过程。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/apps/web/src/alpha-app.tsx)

我建议保留离散结算，增加一个**可跳过的短演出队列**：

> 角色到位 → 开始工作 → 进度变化 → 发生事件/完成任务 → 显示本时段摘要。

这一建议属于对 GDD 播放节奏的调整，应记录为设计决策，而不是静默修改。初期不必强制执行约 60 秒播放。

重要边界是：**演出速度、跳过动画、切换场景不能改变经营结果。**

### 6. 角色与故事界面：避免一次展开所有系统

伙伴首页只展示当下最重要的状态和操作；版本成长、训练、故事放入明确的分区。

故事未解锁时，显示标题或线索即可，不要直接展开全文再禁用选择按钮。当前源码是先展示剧情文本，再按好感等条件禁用选项，容易提前泄露内容。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/apps/web/src/alpha-app.tsx)

同理，结局与远征可以保留入口，但前期不要让玩家在手账里看到整套后期系统和所有结局条件。让它们随着章节逐步进入视野。

# 五、美术与动画下一步怎么做？

## 1. 原版 AI-Village 角色应当成为固定基准

**不再重新设计 12 位角色，不再用一批新立绘替代现有形象。**

最新仓库已经明确要求保留原服饰与身份，版本成长目前使用文字标记，不再叠加会改变造型的新装饰。这是当前项目比早期 GDD 更明确的视觉决策，应优先遵守。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/docs/VILLAGE_CHIBI_ACCEPTANCE.md)

后续需要做的是动作与表现，而不是换人。

## 2. 优先解决“人物、家具、背景没有充分结合”

现有车库背景已经具备暖色木质、绿植、窗光和现代工作室的氛围，可以继续使用。美术生成规范也明确预留了下半部地面，供独立角色与桌椅摆放。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/apps/web/public/art/garage.webp)

问题不在于背景需要重画，而在于角色目前主要按屏幕宽度和人数排成阵列。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/apps/web/src/scene.ts)

建议下一轮先给三个场景建立固定锚点：

| 场景 | 优先制作的锚点 |
|---|---|
| 工作室 | 四个工位、白板、休息角、入口 |
| 食堂 | 餐桌、取餐点、饭锅、入口 |
| 图书馆 | 阅读座位、书架、讨论桌、入口 |

角色根据活动占据这些位置，再由表现层沿简单路径点移动。

**这样比先增加广场、商场、超市，更能让现有世界“活起来”。**

自由装修和复杂寻路可以继续后置；固定工位已经足以展示硬件升级、角色协作和忙闲状态。

## 3. 动画先覆盖四位初始角色的高频动作

当前纸娃娃基础动作主要是根节点位移、身体旋转以及表情切换。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/apps/web/src/village-characters.ts)

下一轮建议优先做以下动作能力：

| 动作 | 玩家应看到什么 |
|---|---|
| 待机 | 呼吸、轻微视线或身体变化，不像静态贴图 |
| 工作 | 手部与键盘/书本位置匹配，不只是整个人摇动 |
| 思考/审查 | 阅读、停顿、查看资料，与执行者有区别 |
| 用餐 | 手、餐具、碗和桌面关系正确 |
| 移动 | 从入口走到工位或餐桌，有起止和方向反馈 |
| 结果反应 | 参与交付者庆祝，受事件影响者惊讶或沮丧 |

其中最后一项也需要调整代码：当前场景会根据全局未决事件或最近交付流水，让场内角色统一进入惊讶或庆祝状态。更合适的是让领域事件携带受影响角色和任务标识，只让相关人物反应。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/apps/web/src/scene.ts)

优先复用已有部件，通过程序化动画完成。只有现有部件确实无法表现某个动作时，再补对应手势或道具，不要一开始就为 12 人制作全套逐帧动画。

## 4. 家具与道具的统一，优先级高于新背景

下一批美术资源建议集中在：

**工位、椅子、显示器、键盘、书本、餐具、饭锅、白板、休息座椅，以及少量工作特效。**

目标是让它们在描边、阴影、透视和细节密度上与原角色及背景协调。

特别要检查桌面遮挡、脚底接地、手部位置和前后层级。这些问题比角色多一套衣服更影响整体完成度。

## 5. 将“升级”变成看得见的成长

现有软硬件系统已经可以作为视觉成长的依据。下一步可以先做三档工位表现：

> 临时桌椅 → 正常工作站 → 多屏协作工位。

算力升级可以改变机箱、服务器角落和指示灯；存储升级可以增加资料架或设备；团队规模扩大可以开放新工位。

这能让玩家感受到“赚到的钱改变了工作室”，而不是只看到等级从 1 变成 2。

不建议现在就上完整家具编辑器。先完成**规则状态驱动的固定布局升级**，成本和测试范围更可控。

## 6. 美术资源需要另做运行时优化，但不要破坏母版

当前记录显示，原版 PNG 角色资源约 25 MB，完整试玩 ZIP 约 89 MB；后者还包含多个宿主产物，**不能直接等同于 Web 首屏下载量**。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/harness/village-chibi/package-results.md)

建议分别测量首屏传输、纹理解码、内存和切换场景开销，再建立优化版资源：

- 原 PNG、角色定义、枢轴与来源哈希保持不动。
- 压缩图集单独使用新的资源版本。
- 优先加载当前场景和开局角色。
- 用同一组动作截图比较透明边、表情、层级和清晰度。

仓库现有记录也明确尚未完成晚期 12 人同屏和低端设备性能验收，应该补这部分，而不是只继续做静态资源校验。[raw.githubusercontent.com](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/docs/VILLAGE_CHIBI_ACCEPTANCE.md)

## 7. MiniMax 暂时不是主线依赖

这一轮主要问题是纸娃娃动作、家具关系和场景反馈，优先由现有资源与程序化动画解决。

MiniMax 可以留给后续独立的片头、梦境、远征氛围或短演出实验，但不要让视频生成成为核心开发的前置条件，也不要用生成视频替代可交互角色动作。

音频则可以先补一套小规模方案：工作室背景音乐，以及接单、开始工作、事件、交付、升级、错误提示等声音。不需要立刻加入真人配音或全员语音。

# 六、推荐的下一阶段开发顺序

我建议新增一个明确的阶段名称，例如：

## `Productization A：第 0 章完整体验`

不要继续用“M5 已完成”作为本轮工作的起点描述，而是使用下列可交付任务。

| 顺序 | 工作包 | 主要交付 | 验收重点 |
|---|---|---|---|
| A0 | 当前基线整理 | GDD 对照表、当前开放项、明确视觉基准 | 现状只有一个权威入口，不混用历史“最新”记录 |
| A1 | 内容一致性修正 | 类别/权重/描述/需求/评级一致性检查 | 玩家按文意选人不会被配置误导 |
| A2 | 核心决策 UI | 委托分类、派遣工作台、时间表达、结算反馈 | 不读 GDD 也能理解接单和派遣 |
| A3 | 第 0 章精选内容 | 约 12 份委托、少量精品事件、开局引导 | 有不同策略，而不只是重复推进 |
| A4 | 角色生活与动作 | 三场景锚点、四角色高频动作、状态反应 | 工作、吃饭、阅读和休息能看出区别 |
| A5 | 场景成长与资源优化 | 家具统一、工位升级、加载与同屏测试 | 保留原角色风格，运行表现稳定 |
| A6 | 正常数值完整游玩 | 第 0 章到第 1 章流程，失败补救，存档恢复 | 不改钱、不改属性、不跳章节仍能推进 |

**A1、A2、A4 可以在接口确定后并行；A6 不必等所有美术完成才开始。**

后续第 2–4 章保留现有代码，不删除。等前两章形成质量标准后，再逐章检查和深化，而不是同时重写全战役。

# 七、为了保持连续开发，分工应该怎么安排？

## Codex + Astra：主实施与集成继续保持单一负责人

主线程优先负责：

**核心规则修正、内容结构、派遣预估、领域事件、UI 接入、存档与回归测试。**

不要因这次 UI 改造再拆出大量新包。当前可以先在 Web 应用内部拆分委托、伙伴、经营、手账和弹窗组件，让每个模块更易审查。

场景代码现在每次更新会清理并重建显示对象。后续加入更多动作和角色后，建议改为按角色 ID 保留实例、按变化更新，但应以测量结果决定优化力度，不能仅凭这一写法就断言已有内存泄漏。[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/apps/web/src/scene.ts)

## 内容与美术可以独立推进，但不能各自定义规则

内容线程只修改选定的内容文件和编辑规范；美术线程只修改资源版本、场景锚点和动作配置。

委托 Schema、领域事件类型、角色标识、存档协议由主线程统一负责。

例如，美术线程可以制作“交付庆祝”，但不能自行通过余额变化猜测交付成功；内容线程可以写“客户要求改手机端”，但必须使用已定义的需求效果，而不是在文案里写了、规则里没发生。

## 审查沿用仓库最新的 Gemini 统一复审安排

虽然最初计划包含 Gemini、Opus、Sonnet 多路审查，但仓库当前已经明确本轮由 Gemini 统一复审，主线程唯一集成。**我建议本轮先沿用这个安排，不重新增加一轮重复的全面审查。**[GitHub](https://raw.githubusercontent.com/Nidofy/out-of-tokens/codex/m1-foundation/harness/reviews/gemini-unified-2b47242-prompt.md)

Opus 后续更适合承担独立的内容与经营体验专项，审查问题应具体到：

> 这份委托能否产生两种合理方案？  
> 角色差异是否真实存在？  
> 失败是否可以理解和补救？

而不是再次泛泛检查同一批基础代码。

即使暂时没有外部测试者，也可以继续推进内容、交互和技术验证；但保留“真人试玩未完成”的状态，不把自动操作和 AI 评价折算成真人测试人数。

## 给下一轮开发的明确结论

**继续按 GDD 推进，但把推进方式从“增加功能覆盖”改为“兑现核心体验”。**

现在最值得投入的不是新模型、新角色、新世界或微信移植，而是把以下过程做好：

> 玩家读懂一份委托，发现隐藏问题，选出合适的团队，看着原版 AI-Village 角色真实地工作和生活，得到可解释的结果，再用收入改善工作室。

**下一轮最优先的三个交付，应当是：内容与规则一致、派遣与交付界面可理解、三场景中的角色行为可信。** 这三项完成后，现有的大量系统才会真正转化成玩家能感受到的游戏内容。
