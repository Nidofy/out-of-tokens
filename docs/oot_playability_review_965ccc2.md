# Out of Tokens：可玩性、易理解性与上手体验审查

## 0. 基线与证据范围

- 审查对象：公开仓库 Nidofy/out-of-tokens，默认分支 codex/m1-foundation。
- 最新公开 STATUS 为 2026-11-16 的 Living Studio 3.0 Wave 2 / UI/UX 2.0；关键实现固定到已核实的提交 `965ccc2b39fcbb08af8339032af5bc0c1996fe31`。此处不将该实现提交未经核验地称为所有交接文档的最新 HEAD。
- 方法：读取公开源码、内容配置和状态文档；对首单质量、深夜活动与恢复、新手手册初始化做独立算术/控制流复算。
- 未进行：完整仓库构建、全量测试复跑、真实玩家试玩、留存或操作耗时测量。
- 仓库报告的测试通过与视觉验证是仓库证据，不是本次独立执行结果；外部证据目录未作为已查看的截图。
- 下文标为“建议”的内容不是现有功能，也不是已经验证有效的玩家数据。

## 1. 结论

下一阶段应做“可玩性与上手体验整合”，而不是继续增加系统数。当前已有委托、条件预估、范围协商、项目路线、伙伴档案、礼物偏好、搭档、群聊、客户评价和生活演出。关键是把它们连成：理解要求 → 有依据地选人 → 看见工作与结果 → 知道原因 → 对伙伴或工作室产生新的期待。

保留 UI/UX 2.0、现有角色资源和视觉冻结约束。不再以换主题、加地图、加新货币、接大模型作为本轮完成标准。

## 2. 已实现的基础，不应重复开发

1. `commission-workbench.tsx`：需求与组队区、岗位和部署选择、预估、能力权重、错误解释、跳往办公室/财务并保留队伍草稿。
2. `partner-profile.tsx`：伙伴舞台、状态、版本、成长、故事与生活操作。
3. `living-adapter.ts` / 核心 campaign：礼物偏好、搭档解锁与实际生效条件、客户类型、工作和生活回应。
4. `messenger-drawer.tsx`：免费且不占时段的群聊回复，一次性奖励，不是无限刷取。
5. `projects-b1.json`：社区书店的系统与服务手册两条路线，能力、分期、反馈不同。

## 3. 优先问题与证据

### F01：第一单考察了玩家尚未学会的质量规则

来源：`content/campaign/commissions-m5.json` 的 menu、`versions-m2.json` 的四个初始版本、`packages/oot-core/src/simulation.ts` 的质量结算。

menu 要求写作0.7、资料0.3，及格线60。仅作单人执行、无审查、无隐藏需求、无缺陷、无额外奖励/事件/搭档加成，且已完成工作量时：

| 角色 | 基础质量 | 加入±5波动的参考范围 |
|---|---:|---:|
| DeepSeek V3 | 57 | 约52–62 |
| Qwen 2.5 | 67 | 约62–72 |
| Llama 3 | 57 | 约52–62 |
| Mistral 7B | 54 | 约49–59 |

这是条件复算，不是实际成功率。Qwen 仍可能受缺陷、资源、时间等影响；Mistral 的结论也不适用于有额外加成或审查的方案。

问题不一定是数值错，而是新玩家可能以喜爱、速度或价格选择首位伙伴，却不知道某种单人方案在上述条件下达不到及格线。

建议：首单明确显示“为什么此人适合”和质量线；提供可改的示例队伍。第二个教学委托可使用已有低门槛双语告示，让快而省的角色展示价值。不要让所有角色首单同样强，也不要暗改结果确保成功。

### F02：深夜社交的机会成本没有同等明确地展示

来源：`campaign.ts` 的 chat/gift/meal/study/story 与 `simulation.ts` 的恢复分支。

面对面聊天、送礼等将 `busyUntil` 设置为当前时段+1。深夜恢复要求角色没有工作且 `busyUntil <= absoluteSlot`，恢复精力并清空负载。

隔离例：深夜开始E40、心情70、负载5，无此前加班、事件、高饥饿/压力惩罚、现金危机：

- 不安排活动，推进：E100、心情73、负载0。
- 先面对面聊天，再推进：E40、心情75、负载5。

群聊回复不同：它早返回，不占时段，不能混为一谈。

建议先改表达：明确“占用一个个人时段”“今晚这样做将跳过睡眠恢复”。提供不耗时群聊或晚间再安排的入口。若以后拆成免费寒暄和付费深聊，这是规则改动，要单独审批和测试，不应混入视觉修复。

### F03：新手手册与学习进度关联过弱

来源：`apps/web/src/onboarding.tsx`。

手册初次挂载时，只要有任一已交付任务就默认折叠；隐藏偏好来自全局 localStorage key，可能沿用到新周目。不是说同一会话一交付就立即消失，而是重载/重新初始化行为如此。

建议按学习节点记录引导：接单、队伍、推进、验收、澄清、休息、账单。允许跳过、重开和恢复；不要把“第一单已交付”等同于“掌握全部规则”。按钮由“去看看”改为具体动作。

### F04：状态名不等于下一步真实执行结果

来源：`apps/web/src/ui2-logic.ts`。

推进器先检查 workingCount，再检查夜晚；深夜有 working 状态合同但没有加班时，仍可能显示“单推进中”。这不一定是模拟错误，却容易被理解成“按下去就继续做单”。

建议建立只读 `NextPeriodPreview`：谁工作、谁休息、哪些有条件完成、哪些接近截止、会触发哪笔账单。预览不得消耗 RNG、提交命令、泄露隐藏结果。夜间明确区分“合同进行中”和“此时段执行工作”。

### F05：群聊的未读和未回复没有分开

来源：`apps/web/src/messenger-drawer.tsx`。

当前 `chosenReply === null` 同时驱动未读点和待回复奖励提示。玩家读过但不回复，红点仍然存在。奖励每话题一次，不是无限漏洞。

建议：阅读状态与选择回复分开；非紧急聊天允许已读、稍后、忽略。不要把休闲聊天变成每天必须清的数值任务。

### F06：普通 Web 的退出恢复承诺还不够明确

来源：`apps/web/src/use-game.ts`。

常规 Web 的 send 路径自动存档条件主要是 DayEnd/Restarted；DSH/desktop 路径不同。不能假定接单、派遣、送礼、群聊和交付之后已自动落盘。本次未在完整浏览器重现刷新丢进度，因此作为源码支持的风险处理。

建议：重要领域命令检查点或合并后的自动保存；保留串行写入、修订校验和多标签冲突保护。显示最后保存时间/状态，存储失败给出可导出的恢复路径。不要只依赖 unload。

### F07：内容更新会影响旧存档导入

来源：`packages/oot-persistence/src/shared.ts`，STATUS兼容性说明。

decode 对 schema、engine、contentVersion、contentHash 严格匹配。保持 engine/content 标签不变并不等于内容指纹兼容。

建议：面向试玩先固定测试内容版本；保留旧版运行路径或明确的迁移方案。不删除哈希检查，不假装旧命令一定能在新内容下得到相同结果。未来机制/风味版本分层应另做协议设计。

## 4. 第一轮体验重排（建议）

目标：让玩家先感到“我的选择有用”，再理解完整系统。以下分钟数是设计目标，不是实测用时或开发工期。

| 阶段 | 当前资产可支持的体验 | 玩家学到什么 |
|---|---|---|
| 开场 | 四位伙伴、一份清楚委托、一句欢迎消息 | 我是负责人，不是亲自写代码 |
| 首单 | 菜单、可修改示例队伍、明确验收线 | 能力匹配与质量约束 |
| 首次交付 | 客户使用反馈、贡献解释、伙伴反应 | 为什么成功，钱从何而来 |
| 第二种选择 | 双语告示或小型开发委托 | 便宜/快/稳有适用场景 |
| 首次需求谜题 | 类似微信的网站，已有缩小/分期方案 | 懂需求比盲目加人有价值 |
| 休息与成长 | 下一时段预览、伙伴互动、可见小升级或搭档进度 | 工作室不只是资金进度条 |

先在UI中渐进显示，不强制删除进阶功能。熟练玩家随时进入完整界面。若固定新手牌组、事件规则或奖励，需作为独立内容版本记录。

## 5. 提高策略乐趣：降低操作，不替玩家做决定

### 三套可比较的草案

在当前预估上增加“省资源、稳质量、赶交期”候选方案。只给符合条件且有真实差别的方案，不凑三个名字相同的结果，不默认展示隐藏真实需求。

每个方案说明一个优势和一个代价。显示换人前后差值，例如预计工期减少、资源增加、质量下界变化。继续允许手动岗位和部署调整。

候选方案生成复用核心预估与约束，不能在前端另写一套近似结算，也不能操纵游戏RNG。不存在合理方案时明确“当前人员/预算下没有可承诺方案”，指向澄清、缩范围、换时间或拒单。

### 减少重复配置

支持上次队伍/常用搭档草案，但重新验证占用、版本、工位、资源、合同限制。没有玩家确认不得自动接单、自动花钱、自动加班。

“休息到明早”仅作为逐条推进命令的安全封装，遇到事件、重要截止、验收、账单异常等边界停下，不能跳过核心逻辑。

### 澄清应该像调查，不像重复掷骰

已有网站任务及范围提案足够作为样板。先在文案/界面中突出矛盾线索与澄清成本。之后若增加结构化提问、失败后的最低进展或有限次保底，须作为新的规则试验，不能把设计建议写成已实现。

不应让所有委托都强制澄清：懂行甲方可以快进，小白甲方需要判断，已合作的客户可复用知识。

## 6. 角色吸引力：让人物记得具体发生的事

现有即时回应主要按动作键和好感档位选择；不是说已写的60段故事没有质量，而是进一步连接经营事件的空间仍然很大。

建议优先串起一条短链：共同交付 → 与这份任务相关的双人对话 → 共享交付进度 → 搭档茶会 → 下一份合适任务中看见协同效果。

客户回信也应优先引用实际交付：选了小范围方案、避免重复提交、保留维护说明等。社区书店现有真实使用反馈就是可推广样板。

所有文本从真实任务/事件状态取值，未发生的事不写成回忆。用人工模板和事件标签足够，不需要新增大模型、真实API花费或生成式记忆系统。

礼物保持偏好发现的趣味。奖励说明可见，但不应压过人物回应；茶歇与群聊不要演变为固定每日打卡。好感数字不应该成为玩家照顾伙伴的唯一理由。

## 7. 表达和操作规范（建议）

- 委托首屏三件事：要做什么、何时交、建议关注什么。WP/权重/缺陷公式放详情。
- 派遣结果优先回答：能做吗、能按时吗、预算够吗；风险可展开，不改成虚假的精确成功率。
- 下一时段不是一个抽象时钟按钮：简洁预览工作、休息、截止和账单。
- 当前目标最多一个主目标，另有一个近期期待；不要首屏同时展示完整科技树、远征、所有结局条件。
- 结算区分预付款、尾款、已付额度、临时购入、待结电费，避免把库存额度消耗当作再次支付现金。
- 当前净偿付资金为现金减贷款及未完成订单预付款；它不是净利润，也不自动等于未来账单后的余额。名称和说明必须准确，未来支出单列。
- 失败说明列真实来源及可行补救，不给每个负面随机数都叠一段抽象梗。
- 短回执可跳过，重要选择不自动替玩家做；普通成功不连续弹多层提示。

| PLAY-02 | P0 | onboarding | 学习节点、重开/跳过/恢复 | 首单后重载不误判已掌握全部；新周目偏好有明确策略 |

| PLAY-09 | P1 | journal/finance | 当前目标、风险与账目解释 | 玩家能说明现金与净偿付资金不同之处 |
| PLAY-10 | P1 | persistence/发布策略 | 版本兼容与迁移承诺 | 旧存档不静默删除；拒绝/迁移/旧版继续三种路径明确 |
| PLAY-11 | P2 | commands包装、UI | 重用队伍、安全推进 | 重新校验；事件/截止/验收处停下；不绕过模拟 |
| PLAY-12 | P2 | 数据与测试 | 澄清设计/策略平衡小试验 | 单独版本与对照，不混入视觉修补 |

先做不改变领域规则的P0/P1：指引、说明、预览、保存、状态表达。内容及经济规则变更单独建分支/版本，保留确定性与历史轨迹证据。

## 9. 可玩性验收而非只有代码验收

建议首轮邀请6–10人，既有AI工具熟悉者也有不熟悉者；人数只是早期发现问题的规模，不支持市场留存估计。

不预先讲解全套玩法。请他们尝试接单、派遣、完成首单、说明失败/资源/休息，再自行决定是否继续。记录“在哪一步犹豫或请求帮助”，不要只收集总体评分。

可讨论的内部目标（不是行业标准）：

- 10名测试者中至少8人能在约10分钟内、不经开发者提示完成首个闭环。
- 至少7人能解释一次选择为什么成功/失败，以及深夜活动与恢复的区别。
- 至少6人在无催促、无额外奖励承诺的情况下，自愿接第二单。

观察漏斗：到达主界面 → 看首单 → 试配队伍 → 接单 → 派遣 → 推进 → 验收 → 第二单 → 离开 → 正确恢复。日志默认本地、可选择导出，不采集无关个人输入或真实会话。

每个方案至少补：明确客户、模糊客户、资源不足、期限紧、精力低、睡眠被占用、未解锁搭档、已解锁但条件不符、一次失败和补救。继续保留全量规则测试，但不把自动化通过当作“好玩已证明”。

## 10. 本轮不建议扩展

不增加新地图和新的生活需求条；不增加每日登录/红点清理任务；不靠抽卡或新货币推动留存；不引入实际LLM费用作为游戏进展条件；不为了让所有人新手过关而削平全部角色差异；不再重做一整套视觉主题。

目标不是让玩家更忙，而是让玩家每次操作都知道自己为什么做，并愿意看看伙伴下一次会发生什么。

## 11. 可复算材料

同包中的 `rule_probes.py` 与 `rule_probe_results.json` 仅用于首单质量、深夜恢复及手册初始化的隔离验证。不代表仓库全量测试。
