## 独立发现

### VC-R1 / P1：重复同步目标会中断起身，造成约47px脚底跳变

位置：Gemini工作树 `apps/web/src/office-scene-spec.ts:161` 的 `syncWorkstationTarget`。旧工位退出分支处理seat/work/部分approach，却漏掉正在进行的stand；再次同步相同休息目标时落到173行，清空station并变成idle。换工位目标再次同步则落到166行，直接替换station并开始approach。

真实触发路径存在：`office-scene.ts` 的镜头平移/滚轮、尺寸变化以及view/capacity变化都会调用sync，再同步每个角色的目标。这些同步应保留未完成的起身/离开进度。

独立调用实际导出函数的 `trajectory-audit.ts`：起身100ms后重复同步同一目标，时间步为0，离开工位和换工位两种情况均从脚底747.769跳到795，差47.231；不重复同步的对照保持stand及原脚底值。脚本按预期返回失败，输出 `trajectory-audit.json`；这不是仓库479项测试的通过结果。

真实 `createWorkshop` 仓外探针复现：GLM、Tier3、depth620、arrived=.5；可信按钮仅重复提交相同休息view，stage由stand变idle，脚底573→620，zIndex620→624。证据 `tier/stand-before.json`、`stand-after.json` 及对应截图。无产品修补、无合成事件。这是验收阻塞，Gemini须修复并覆盖重复同步、途中改目标、返回旧工位等序列。

### VC-R3 / P2证据修正：来件工作相位没有推进动画时间

来件 `tier-dynamic/tier-probe.js` 先 `app.ticker.stop()`，再用 `tick(350)` 标注work-phase-.35/.7。但生产 `elapsed` 只在app.ticker回调中递增，直接tick不会推进它。因此原工作相位标签不证明实际覆盖不同动画相位；原 `maxFeetError=0` 也只证明单帧渲染锚点与期望坐标一致，不证明相邻帧无跳变。

独立仓外构建显式设置elapsed为0/.35/.7后重跑全部1152样本，统计仍无眼口ROI相交；修正记录在 `tier/probe-amendments.json`。需Gemini修正后续取样脚本和证据措辞；该诊断修正不解除VC-R1。
