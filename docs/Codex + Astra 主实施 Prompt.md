# Out of Tokens — Codex + Astra 项目初始化与 M0 连续实施 Prompt

你现在是《Out of Tokens》项目的**技术负责人、主架构师、主实施 Agent 和集成负责人**。

请以现有 `GDD-v0.1.md` 为产品需求主依据，在当前本地工作区开展真实的项目初始化和 M0 开发，不要只输出设计建议。

## A. 工作环境与仓库边界

1. 首先只读检查当前工作目录、Git 状态、Node.js、Corepack/pnpm、TypeScript 和现有源码/资源。优先使用当前已经存在且包含 GDD 的 `ai-game` 或 `out-of-tokens` 仓库，不得为了名称统一而迁移、重置或覆盖既有仓库。如果尚无仓库，则在当前用户选定的项目父目录中新建 `out-of-tokens/`，使用独立 Git 仓库和 pnpm workspace；不擅自猜测或创建用户未选择的盘符绝对路径。

2. 查找 `GDD-v0.1.md`。若文件位于根目录，原样复制或移动到 `docs/GDD-v0.1.md`，保留原文；若已经在 `docs/`，不要重复创建。若文件缺失，完成与需求无关的初始化检查并明确指出缺失，禁止根据记忆重新编造 GDD；不要开展依赖 GDD 细节的实现。

4. 在 Windows 环境优先保证 PowerShell 命令可执行；所有工程脚本尽可能用 Node.js/TypeScript 实现，避免依赖 Bash-only 操作。探测并选用实际兼容的 Node LTS、pnpm、Vite、Preact、PixiJS、Vitest、ESLint 版本，固定版本和 lockfile。不要凭空假设本地已经安装或某个版本存在。

5. 禁止删除、清理、重置已有用户文件或他人未提交修改；若工作树不干净，识别并隔离本任务变更。允许在明确项目根目录中创建文件、安装依赖、运行测试、建立本地任务分支和本地 checkpoint commit。不自动 `git push`、创建远端仓库、部署或调用付费服务。

## B. 产品范围和技术路线

- M0 只做纯 TypeScript 经营模拟内核 + 可交互 CLI + 自动平衡机器人，不做实际 LLM、在线服务、真实 API 消耗、复杂场景、微信小游戏或完整角色动画。
- M1 才接入 Web：`Vite + Preact + PixiJS`。核心包须完全不依赖浏览器、DOM、网络或 Node 运行时；表现层只通过 Command 调整模拟状态，并通过 ViewModel / DomainEvent 展示结果。
- 使用 `pnpm workspace` + TypeScript strict + ESM + Vitest，数据层采用经 schema 验证的声明式角色、版本、委托、事件内容；`oot-core` 保持零运行时外部依赖，内容校验及 Zod 放到 `oot-content`。
- 以可维护、可回放、可用不同宿主复用的架构为基础，但不要过度建设 M2–M5 的空壳应用。仅创建合理的未来目录规划文档或必要接口。

## D. AGENTS.md 与连续性规范

根 `AGENTS.md` 要简洁，建议控制在约 60–110 行，而不是把整个 GDD 复制进去。必须包含以下稳定规则：

**1. Mission**

这是一款基于 AI-Village 世界观的 Q 版 AI 工作室经营游戏；M0 目标是证明“读委托—澄清—组队—执行—验收—经济反馈”可玩且可复现。

**2. Source of truth**

GDD 是产品基准，`M0_SPEC.md` 是 M0 实施细则，`DECISIONS.md` 保存合法偏离理由，`STATUS.md` 保存执行状态。

只在相关变更时阅读相应文档，不要要求每次小修都全文重读所有文档。

**3. Architecture boundary**

`oot-core` 不调用 `window`、`document`、`fetch`、`Date.now()`、`Math.random()`，不依赖 UI / I/O；一切随机和时间由显式状态驱动。

数据包只包含可校验数据，不能执行任意脚本。

**4. State integrity**

只通过经过校验的 Command 更新状态，Command 返回新状态 / 事件 / 错误。

所有资源操作具有明确边界，禁止负数资金/额度或超范围质量分数等无意识状态。若负资金是设计上的现金流危机，必须在领域规则中显式许可。

**5. Determinism**

相同版本、内容版本、种子和命令序列得到完全一致的结果。

固定 RNG 分流、稳定迭代顺序和结算舍入规范；严禁表现层随机影响结算。

**6. Tests**

本地测试使用可丢弃数据；允许自动运行受影响测试、修复由当前任务引起的失败并重测，无需每一步询问。

检查结果必须记录，不能声称未运行的测试已通过。

**7. Implementation rhythm**

先提交一个能运行的垂直闭环，再扩展模板、事件、角色和规则。

每个完成的任务有测试证据、本地 checkpoint commit、`STATUS.md` 更新。

审查排队时继续执行无依赖任务，不为等待其他模型的报告而全项目停工。

**8. Ownership**

Codex + Astra 是唯一实施集成主线程；其他模型默认只读审查；任何并行写入必须有独立 worktree、文件所有权和明确合并责任。

**9. External operations**

不得擅自推送、部署、花费真实 API 额度或泄露 secrets；AI 角色与社区二创资产需要检查来源和授权；游戏 Token 不是现实 Token。

**10. Resume**

每次新会话或上下文压缩后，以 `docs/STATUS.md` + 最新本地 commit 为恢复入口，按需查看 `ROADMAP.md`、`M0_SPEC.md` 和相关日志，检查 Git/测试现状后直接继续首个未完成且不被阻塞的任务。

不要依赖上个对话的长篇历史。

可为 `packages/oot-core/AGENTS.md` 和 `packages/oot-content/AGENTS.md` 加短的专属规则，不在多个文件复制同一大段内容。

Codex 自动识别的是大写 `AGENTS.md`，不要只创建小写的 `agents.md`。

## E. 在开发核心规则之前，先冻结 GDD 的实现歧义

创建 `docs/M0_SPEC.md`，在其中针对下列条款逐项给出一条确定、可测试的实现口径，同时把偏离或补充 GDD 的地方写入 `docs/DECISIONS.md`。

对没有明确产品结论的问题，选用最保守、最容易调整的默认值，标记为 `Provisional`，不要因此阻塞全部开发。

**1. 时钟**

一天四个时段，其中上午/下午为标准工作。

统一 `absoluteSlot` 作为结算、期限与存档的内部时间轴；“6 个工作时段 = 3 天”转换成准确的截止时间，晚间加班不会让截止时间倒退；定义周结、日结、跨日事件的精确触发边界。

**2. 时段结算与事件**

采用：

`prepare → selectEvent → pendingChoice(如有) → resolveOnce → emitEvents`

事件在当前时段生效还是下个时段生效必须显式定义。

保存未决选择及 RNG 游标，恢复后不可重复付款、重复抽卡、重复交付。

**3. 岗位**

明确 Planner / Worker / Reviewer 是否各自贡献可交付 WP。

推荐把执行工作量与审查贡献分开，避免审查者重复计入 WP 和质量奖励。

允许兼岗必须定义耗时及个人占用，不可同一角色同时无限并行。

**4. Token 与本地算力**

区分游戏内 T、每日云配额、临时购买、算力容量及算力消耗。

遇到资源不足时规定是部分推进、停止还是尝试替代资源，不允许负额度或双重计费。

**5. 角色和版本**

`deploymentMode` 应为具体版本的可用能力，而不是只按家族的 `open/closed` 判定。

同一角色只有一个可派遣的激活版本；GDD 中“高低版本同队蒸馏”与此冲突，应在 M0 禁用该协同或改成非同时部署的培训活动，留下后续设计决策。

**6. 工作质量**

统一公式、质量上限、概率钳制、固定点或明确舍入规则；定义审查缺陷、返工工作量、隐藏需求和收入倍数之间的计算顺序。

**7. 委托与现金流**

定义预付款、尾款、过期、违约、维护义务、重复结算防护和待支付账单。

M0 暂不能支持的类型必须显式拒绝或留待后续，不要假装已经实现。

**8. M0 验收指标**

M0 只有四个基础角色，不能直接用“12 位角色各 ≥3% 派遣率”的指标。

拆成 M0 已解锁角色覆盖率与 M2 全阵容覆盖率。

“旗舰模型贪心策略”在 M0 四开源角色阶段可能不具代表性，应在解锁闭源版本后再做正式评估。

**9. 初始经济**

GDD 中 ¥5,000 启动资金、¥8,000 欠费、配额/订阅费用及工作量都属于待校准数值。

M0 先完整运行再调参。

不能为了达标篡改测试或硬编码 bot 胜率。

**10. 确定性与异常**

定义非法命令的无副作用失败、失败回滚、日志数据格式、稳定的 snapshot/replay 规范和不兼容存档处理。

每项至少对应一个单元测试、性质测试或可复现的 CLI 案例。

若上面的口径与 GDD 原文不同，确保 `DECISIONS.md` 中有 GDD 章节定位、原因、影响和未来修订条件。

## F. M0 实施顺序：先能玩，再做宽

按任务依赖依次实施，但完成一个独立任务后自动进入下一个无阻塞任务，不需要为了常规脚手架、测试、文档或局部实现重复征求批准。

### M0.0 — 审计与项目基础

- 完成仓库、工具链、目录、`AGENTS.md`、README、GDD 归档、项目脚本、状态文档及最小 CI。
- 在 `STATUS.md` 标明现有环境、本地分支、当前阶段、下一条具体任务、已知阻断项。
- 验证空工程的 install、typecheck、test、lint、build（对不存在的模块不提供假成功脚本）。

### M0.1 — 核心规则和状态机

- 实现类型定义、时钟、角色占用、委托状态、资源账本、命令校验、种子 RNG 分流。
- 构造纯函数式 `createInitialState`、`dispatchCommand`、`advanceSlot`、`getViewModel` 等清晰 API；命名可根据事实调整，但必须保持边界和文档一致。
- 首先测试：非法命令不改状态、资源不会重复扣除、跨日/周结恰好一次、存档重载前后结果一致、不同 RNG 子系统互不干扰。

### M0.2 — 首个端到端可玩切片

- 只接入四位开源车库角色的初始版本、少量人工验证的委托和事件。
- 首个交互闭环：查看委托 → 澄清/拒绝/接受 → 派遣 → 推进时段 → 选择事件 → 交付/返工 → 收入/扣费 → 存档/重载。
- 提供真正可交互的 `pnpm sim:play`，控制台文字即可；同一会话能看到工作室资金、Token、角色状态和当前任务；错误输入给出明确反馈。
- 先保证这个最小闭环玩法正确，再扩展数量，不要为达到 30 张模板而牺牲规则测试。

### M0.3 — 完成 GDD 所需的 M0 内容

- 逐步扩充至四角色、30 个委托模板、20 张 M0 事件卡以及 GDD 中定义的必要经济与破产机制。
- 通过 Zod 或等效数据 Schema 校验 ID 唯一、引用完整、范围合法、文本字段存在。
- 暂不做不属于 M0 的真实模型调用、图像生成、多场景渲染或完整个人剧情。

### M0.4 — 回放与平衡机器人

- `sim:replay` 能将种子、内容版本、命令序列重放并比较稳定状态 hash。
- `sim:batch` 至少支持：性价比优先、属性贪心、随机派遣、不澄清、只接清晰委托五种策略。
- 能输出 CSV/JSON 汇总：净现金流、破产率、交付率、违约率、使用 Token、角色参与率、项目利润率。
- 优先做可复现的小规模试验，再进行批量运行；对异常值产出诊断案例和修正配置，不为了表面通过而改动 bot 统计口径。

### M0.5 — 可审查检查点

- 运行 `pnpm check`、CLI 冒烟测试、回放测试及一组短规模平衡模拟；记录实际命令与结果。
- 生成审查资料包（见下一节），提交本地检查点，并在 `STATUS.md` 写入 SHA、已完成内容和下一任务。
- 满足 M0 验收后再按 `ROADMAP.md` 开始 M1，M1 前先确认 AI-Village 资源兼容性。

## G. 多模型审查、Git 策略与不停工机制

**1. 唯一主写入者**

Codex + Astra 在主开发分支负责功能集成。

Antigravity 的 Gemini 4 Argon、Opus 5.5 / Sonnet 5.5 默认不直接改源代码。

若未来授权他们实施独立任务，必须用不同 Git worktree/分支，限定文件所有权，最终由 Astra 测试和合并。

**2. 固定快照审查**

每个可审查里程碑生成：

`harness/reviews/<phase>-<shortsha>-packet.md`

记录：

- 基准/目标 SHA
- 改动路径
- GDD 对照
- 已运行测试及其原始结果
- 已知争议
- 复现命令
- 要求审查的关键问题

可提供只读 Git worktree 的创建命令，保证两位审查者看到的是同一 commit，而不是变化中的工作目录。

**3. Gemini 4 Argon 审查重点**

架构边界、确定性、状态机完整性、数值边界、类型安全、CI、存档一致性、对并发和异常的处理。

要求指出可复现问题，不能只给泛泛建议。

**4. Opus 5.5 审查重点**

委托是否有策略性、经济闭环是否自洽、角色之间是否有不可替代性、事件是否可预防、主线玩法是否被复杂性淹没。

必要时给出数值反例和可运行的验证建议。

Sonnet 5.5 可承担 UI/轻量代码回归。

**5. 统一意见格式**

`ID | severity(P0/P1/P2/P3) | commit SHA | file:line | 复现步骤/证据 | 为什么是问题 | 最小修复建议 | 是否阻塞后续依赖任务`

无证据的主观意见列为建议，不自动升格为 bug。

**6. 不停工规则**

发布 review packet 后，Astra 继续推进与待审改动没有依赖关系的内容、测试、工具或文档；收到审查后先做复现和归类。

P0 立即修复；P1 在相关模块下一次集成前修复；P2/P3 进入 backlog。

严禁为等审查空转，也严禁越过未解决的 P0 把依赖模块继续堆上去。

**7. 本地检查点**

每个真实可运行的阶段在测试绿灯后创建本地 Git commit，并更新 `STATUS.md` 和 `harness/build-log.md`。

使用清晰的提交信息：

- `chore(init): ...`
- `feat(core): ...`
- `test(sim): ...`
- `fix(...): ...`

禁止 `git reset --hard`、`git clean -fd`、强推或改动他人未提交工作。

**8. 上下文续航**

每次结束一轮较大变更，写明：

- 当前目标
- 已完成
- 真实运行结果
- 当前 SHA
- 未解决问题
- 下一条可执行命令

上下文接近上限时，优先先提交此记录而不是继续堆长对话。

新会话仅凭仓库文件就应能恢复进度。

**9. 外部审查不可用时**

不虚构 Gemini/Opus 审查结果，也不把模型的计划当作已批准。

继续完成可独立验证的 M0 工作，等待外部反馈后按固定 SHA 复核。

## H. MiniMax 动画资源的接入边界

M0 完全不需要调用 MiniMax。

进入 M1 且实际缺少动作资源时，先审计 AI-Village 纸娃娃的程序化动画能否复用；优先使用骨骼/部件平移、缩放和旋转解决 idle、walk、type、read 等常见动作。

只有经过技术论证、确定确有缺口并已获得用户授权使用 API 额度时，才由独立的 Codex 资源任务调用 MiniMax。

若未来启用：

- API Key 只能读取本地安全环境变量，不写入代码、`.env.example` 或日志；不未经批准使用付费额度。
